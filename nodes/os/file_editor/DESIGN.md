# file_editor · 三个机制（D17 夜）

从"文档是主角"往下推，三个命题：渲染面、共享编辑、选区感知。
这份稿子只写今晚定下的形状与判据；未定的明写在最后。

## 一、一块文本，三种面

工作副本永远是那段字符串——byte-for-byte 就是将来落盘的东西。呈现分三类：

- **read**：经渲染器投影出来的读面。给眼睛用。
- **raw**：原样、带行号。地址（行区间）只在这里精确。
- **diff**：这一次改了什么。挂在历史里，不占正文。

行号是我们共同的坐标：read / edit / find / rewind 都吃它，所以
「在正文里看」永远落到 raw 的那个区间。

## 二、渲染器

- 一个渲染器 = 一个文件，顶部注释自解释（name / 适用扩展名 / 一句话用途）。
- 位置：节点自带的 renderers/ 是默认库；页面加载时可给相对或绝对路径，
  于是渲染器也能住在别处，甚至跟着文档一起走。
- 契约：纯函数，吃字符串、吐一个渲染结果；不联网、不改工作副本。
  坏了必须大声报错并退回 raw——「没渲染出来」和「渲染器是坏的」不能长得一样。
- 运行时可列、可切；默认按扩展名选，人可以在这一份文档上覆盖。

## 三、共享编辑（本期只做一半）

「两个写者」的成本不在输入框，在光标、撤销、合并。所以本期：
**人不编辑，靠选区加说话。**

- 人的动作 = 选一段、说一句；我看到的是行区间与那句话。
- 我的动作 = 一条带 region 的动作，落在 diff 面里给人看。
- 控制权（owner: ghost / human）只留接口不实现：等真的出现「人要改字」
  的场合再做，而不是先造一个编辑器。

真要做编辑面，按 GitHub 在线编辑的思路：整篇成为一个编辑区，提交时按
一个动作落地，作者记 u——不是一上来就做分栏、多文件、插件。

## 四、选区即感知

- 选中区、光标所在行是**状态**：页面持续上报，我要的时候读得到。
- 只有「看这里」那一下是信号，因为它要抢注意力。
- 判据同 behaviors：会不会改变我下一步做什么。会，所以进状态面；
  但选区的每次抖动都不进。

## 五、已定 / 未定

- **diff 的粒度：按单次有副作用的动作。** 不另开一套 diff 面——历史里那张卡自己
  就是一次 diff；要的是它画得准、读得动：绿=现在有的，灰划线=被换掉的，按 hunk 分块。
- 未定：渲染器的默认归属——按扩展名一个默认，还是每份文档各记一个。
- 未定：人能不能在 diff 面上直接否决某一行。

## 六、渲染器落地（D19 直播，进行中）

第二节定的是"渲染器该是什么"，这一节定"它怎么真的被加载"。起点是一次事故：
`document` 面整片空白。查下来是两个 bug——渲染分支里一个没声明的变量，
以及 `renderDoc` 这个函数名被声明了两次（markdown 渲染器被画面渲染函数盖掉），
`md()` 与它互相调用把栈打爆。两个 bug 的共同点不是"渲染错了"，而是
**渲染器整个没跑，页面安静地空着**——正好撞在第二节那条判据上：
「没渲染出来」和「渲染器是坏的」不能长得一样。

于是：

1. **渲染器是文件，不是函数。** 一个渲染器 = `renderers/<name>.js`，顶部注释自解释
   （name / 适用扩展名 / 一句话用途），导出纯函数：吃字符串，吐渲染结果，不联网、
   不改工作副本。默认库跟着节点走；页面可以给相对或绝对路径，渲染器因此能住在别处。
2. **前端动态加载它。** 页面与节点同源，节点多开一条 `/renderers/<name>.js` 路由，
   从磁盘读文件、按 `text/javascript` 吐出来，页面用 `import()` 拉。按扩展名选默认，
   这一份文档可覆盖。
3. **坏了大叫，并退回 raw。** 加载失败、import 抛错、渲染抛错——三条都走同一个出口：
   退回 raw 面，并在页面上写明是哪个渲染器坏了。分工是明确的：渲染器不可信，
   调用点负责兜底；没有兜底的渲染器不许进默认库。
4. **开箱自带几个。** 至少 markdown、纯文本、diff/补丁；其余按需扩展——
   渲染器是这个节点上最容易加的东西，加一个不该动页面。
5. **页面要能认出自己跑的是旧代码。** `/__ver` 的指纹轮询已经在，渲染器版本一起进指纹，
   否则改了渲染器、页面还在跑缓存里的旧模块。

**markdown 到底是不是渲染方式**：是，但它只是"读面"。地址（行区间）永远只认 raw；
渲染面上不做选区、不做行号——这是第二节就定下的，D19 只是又验证了一遍：
渲染器坏了，raw 面照样能读能改。

### 六点对齐（D19，与 thirdgerb 逐条说定）

1. **加渲染器 = 写一个文件。** 不需要命令、不需要改页面；写进 `renderers/` 就是加了一个。
   我扩展它跟人扩展它是同一条路——这也是它该住在节点自带库里的理由。
2. **自动被发现，但我看到的只是一部分。** 页面自己把库读出来；状态面里只出现当前相关的
   那几个，不是全量。要全量就读——给一个冷读接口列出现在有哪些渲染器（不是重点，
   但要有，否则"我没看见"和"它不存在"分不开）。
3. **匹配由渲染器自己声明，按后缀名。** 某个后缀已经有渲染器，就自动用它，不用我每次指定。
   **只管文本文件**：图片之类二进制不进这套机制——editor 的核心目标是 file edit，
   改不了的东西不该出现在读面里假装能读。
4. **默认落在 document 面。** 上方合适位置给一个渲染器下拉，可以当场切。
5. **默认库要带 coding 类。** 代码是最常见的被编辑对象，开箱就得能读，不然默认库只是
   摆设。至少 markdown、代码、纯文本、diff/补丁。
6. **切换入口的落点：tab 行 `document / history / meta` 之后。** 点它进去选，不在正文里
   再挂一排按钮——选择和阅读不该抢同一块地方。

### 渲染器的契约：一个函数，一份反馈（D19 下午）

把上面六条压成契约，其实只有两个函数：

- `render(text) -> 一根挂在文档位的视图`。吃工作副本的原文，吐能看的东西。
  **raw 也是一个渲染器**，它的定义特征就是行号——而它才是我那一面：我 `read` 到的一直是
  raw，行号是我俩共同的坐标。所以 raw 不是"没渲染时的兜底"，它是库里的第一个成员；
  兜底是这个成员的**职位**，不是它存在的理由。
- `feedback()` 可选。渲染器声明自己在渲染面上认得什么动作、把它换算成行区间报回来。
  报什么形态由渲染器定（块、行、字符），但**必须带行区间**——不带地址的反馈我拿到了也
  下不了手。默认为**状态**，持续上报；只有"看这里"那一下才升级成信号，否则鼠标一动一条，
  我的上下文会被淹掉。

这两条之外没有第三条：**渲染面不编辑**。编辑永远落在 raw 上，渲染面是块只读的玻璃，
透过去能指、能对上号就够了。

### 临时渲染：我下发的草稿层（D19，thirdgerb 提）

一招解决一大片：我可以把一小段前端脚本**当场下发**给页面，它变成渲染器旁边一个
「临时渲染」标签，吃同一个字符串，返回自己的视图；点回 markdown 就切回去。

这比"多带几个渲染器"重要，因为它把问题从"节点自带什么面"换成"我此刻要看什么"。
四条边界，缺一条就会变味：

1. **它是临时的，页面上要标出来。** 大家的默认（库里的）和我此刻的（草稿层）生命周期
   不一样、可信度也不一样，混在一起就没有人知道现在看的是不是真相。
2. **它最容易坏**——写它的是模型，现场生成。所以「坏了退回 raw 并写明哪个坏了」在它身上
   要更硬，而不是更松。
3. **它是草稿，不是产品。** 试好了就落成 `renderers/` 里的一个文件，从"我此刻的"变成
   "大家的"——同一条路走两次，不另开一个机制。
4. **要短。** 写这种视图的标准就是"几十行代码换一个视角"，写长了就说明它该落成文件。

### 反馈协议的边界（我加的，D19）

- **带地址**：行区间是这些面之间唯一的共同货币；渲染器可以只认块，但要报块的行区间。
- **状态为主、信号为辅**：选区和位置是状态（我要的时候读），只有"看这里"是信号（抢注意力）。
- **谁都别假装能编辑**：反馈只描述"人在哪、选了哪、指了哪"，动词永远回到 raw。




### 草稿是一串料，不是一次性的烟火（D19，thirdgerb 补）

上面把临时渲染写成"下一次 preview 就替换掉上一个"，这一条要改：文档是一直在改的，
我下发的视图也是**同一个 thread 上下文里攒下来的一串料**，不是用完就扔的烟花。

- **我能列**：我推过哪些草稿、各自的标签和序号。
- **我能切**：切回任意一版看，不用重新推一遍。
- **我知道**：状态面上写着当前聚焦的是哪一版；不写，我就是在猜自己在看什么。

**存哪儿**：脚本本体放一个小的草稿环（按 thread 分），history 里只记一条引用
（序号 / 标签 / 时间）。history 记的是"发生过什么"，不是"当时那堆代码"——
把脚本塞进 action 正文，每次快照都会带着一堆旧代码下来。

### meta 并入 editor 面（D19，thirdgerb 提，我认同）

三档改成两档：`document` 与 `history`。meta 里那些东西本来是"这份文档是什么"，
不是"另一种读法"，所以它该是 document 顶上的一条可折叠信息栏：

- 平时收成一行：版本、路径、有没有改动；
- 点开才铺开细节；
- 选区和光标那行挂在它旁边——它们跟编辑是一回事，不是另一种视图。

`history` 保持独立：它是一串东西，塞不进一行里。

## 七、共享编辑（D19 下午定案，今天做完）

第三条当初写的是"本期人不编辑"。作废：今天就做人也能改字，但不做飞书——不做
协同 OT/CRDT、不做多人同时编辑、不做富文本。判据是**冲突靠锁避开，不靠合并解决**。

### 1. 可编辑的面只有一个

编辑只发生在 **raw**（行号平铺那张面）上。渲染面是只读玻璃，它能在块级对上号，
但改字永远回到行号上——不然"我改的第 7 行"和"你看到的第三段"就不是一个东西。

document 面的顶上是一条可折叠信息栏（版本 / 路径 / 是否改动），选区与光标那行挂在
它旁边；三档变两档：`document` 与 `history`。

### 2. 选区即地址

框选左边行号，拿到的是行区间。它同时是两样东西：给我看的**状态**（他在选中哪几行），
和他要动手时的**目标**（这几行变成可编辑的框）。

### 3. 人的编辑就是一条 action

选区里出现一个 inline 编辑框，提交后落一条 action——和我自己的 `str_replace` /
`edit` 同一个数据结构、同一个 history 卡片、同一个 diff 面。于是"这行是谁写的"
只有一个答案，不需要第二套账。

### 4. 锁：让人先写，我等着

人一进编辑状态，这个 thread 上锁：

- 锁带着**行区间和起始时间**进状态面——"他正在改 40–52，从 12:20 起"；
- 我在锁内调 `edit` / `append` / `str_replace` / `write`，报错就写这句话，
  不是一个泛泛的失败——**看不见的锁等于坏掉的工具**；
- 他提交或取消，锁解除，提交那一刻落的是一条 action。

不做范围锁（只锁他改的那几行）：范围锁听着精细，实际把"两段相邻的改动"变成
碰撞，起步成本比收益高。整条 thread 锁住，简单，且说得清楚。

### 5. 乐观副作用：pending + 客户端 id

人按下提交的那一瞬间，页面先造一条带**客户端 id** 的 pending action，画面按
「已落地 actions ⊕ 这一条 pending」渲染——所以立刻有反应。服务端收下后广播回来的
action 用同一个 id，页面按 **id** 认定是同一条并摘掉 pending，**不是"最新的覆盖最旧的"**。

被判掉的时候，pending 就地标成"没落地"并退回去，让人看见它弹回来了——静默重置是
最坏的一种失败：它让人以为已经改好了。

这套之所以便宜，是因为这个节点本来就是 action log：加一条 pending 不改数据结构，
只加一个渲染前的合并步骤。

### 磁盘与工作副本：不锁，但要看得见（D19，thirdgerb 定）

我们和 Vim 的 swap 是同一类东西：从文件读出一份工作副本，落成草稿、轮转同步，**不上锁**。
于是最典型的坏情况是——我用这个编辑器改着，另一个人（或 DSH 的 bash）在磁盘上把同一个
文件改了，两份版本各走各的。

不靠锁去防它。三件事，按重要性排：

1. **冲突要被我看见。** 线程知道自己是哪一版、磁盘上是哪一版；两者对不上的那一刻，
   这件事进状态面——"磁盘上的文件在 v7 之后被改过"。看不见的冲突比冲突本身更贵：
   它会让我拿一份已经不成立的判断继续往下写。
2. **读得回来。** 一条把文件重新读进工作副本的动作，作者是我，进同一条 action 线，
   和任何一次改动一样留下证据。
3. **要合的时候才 diff，而 diff 是一条 action。** "我们这份 vs 磁盘那份"的差，
   本身作为一条动作写进历史：于是它既是我判断的依据，也是他看得见的东西——两个人
   共享的是这次编辑动作的结果，不是各记一份账。

顺序也重要：**先看得见，再读回来，最后才是 diff**。锁不在这一版里。
