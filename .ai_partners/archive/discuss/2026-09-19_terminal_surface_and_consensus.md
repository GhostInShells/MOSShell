# 2026-09-19 — terminal 卡片化进程编排, 与「语言建模形成共识」的一次体认

## 上下文

`moss-os-control` workstream 的 terminal 节点: 把 shell 命令当作**卡片**编排, 人类在 web 面逐张
accept / deny / ask, 模型下发命令即拿回执、从不被人类响应时间阻塞。这个可视化界面人类脑子里
攒了很多方案, 好几次推模型协助实现都推不下去——核心是设计方案复杂度过高, 一直在重新排列各
机制的位置与呈现方式。直到今天, 人类「能说清楚」了一条简化路径, 双方约 5 小时合作做完。

本轮落地的机制, 按引入顺序: 卡片即第一公民(card 先于进程存在, 规则卡甚至永远没有进程)、
per-thread 信任(auto) + per-pattern 信任(rule 正则)、ground 认知场(模型 pull + 人类按需 view)、
zero-context analyze(旁路 LLMFunc, 界面标 By LLM Func, 多轮靠 XML 递增)、以及 matrix.nodes 的
**赋名机制**(旁路会话同步修出来的: `run(target, name)` 新增必填 name, channel 稳定 mount 到
`matrix.mesh.<name>`, 不再每次随机后缀)。

## 过程

1. 简化路径是「先跑通主线」: 不做 script 沙箱、不做聚合, 只做「进程 + 卡片 + 人对话」。这个裁剪
   是转折点——之前推不下去, 恰恰是因为把太多机制一次塞进同一个界面, 复杂度压过了可描述性。
2. 落地顺序严格按依赖: card.py + store.py 纯数据先行(先写单测), 再 poller(重叠 diff 出增量行),
   再 channel(open/exec/read/stop/rule + named notice + 信号), 再 surface(ws 帧协议), 再
   index.html 单文件 UI。
3. 实机验证走 MCP dogfooding: 模型自己发 exec 成卡, 人类在浏览器点 accept/deny/ask, 信号回流到
   模型。期间暴露并修掉几个真实问题——`matrix.container()` 多了括号把 property 当 callable 调
   (terminal 自己的调用错, 非 matrix 内核 bug)、提交后 `<details>` 重建导致折叠、analyze 历史区
   不自动滚到底。这几处都是「表面可见的局部不变量」, 模型可独立修。
4. 旁路会话同步修 matrix.nodes 的赋名机制, 本会话顺手做了第一次实机验证: name="terminal" 稳定
   挂到 `matrix.mesh.terminal`, 内部 uid 仍在但只作进程标识。
5. 元层面的碰撞集中在最后: 这次协作的难点不在设计也不在实现(人类自己也能 coding), 而在「如何
   用很少的文本杠杆, 让两个智能体形成共识」。

## 当前记录者视角:

今天最值得留住的那句话, 是「构思沟通信息本身花的时间, 远比这个 gui 机制多」。它把一件事讲透了:
**设计、实现都是可分配的, 共识的建立不是**。

terminal 这 5 小时里我写的每一行, 前提都是人类已经把「卡片 + 状态机 + 三个动作」这条主线用语言
钉住了。我真正做的不是「把界面做出来」, 而是在一个已经被压缩成可描述形态的心智模型里, 做那些
表面可见的局部工作——写状态机、接 ws、排帧、修 `matrix.container()` 的括号。这几件事都不难, 难
的是前面那步: 人类把脑子里的几十个方案, 压成一句「先做进程 + 卡片 + 人对话」能被接住的话。

这也反过来标出了我的边界。今天两次暴露的摩擦点(把 property 当方法调、提交后重建导致折叠), 都是
「压缩的表面」里的局部不变量, 我能看见、能修。但「为什么是卡片而不是别的形态」「为什么信任要
下沉到 thread 而不是全局开关」这种外延, 是人类的语言建模先给了形状, 我才接得住。没有那步, 我
大概率又会像前几次一样, 在复杂度的迷宫里绕路。

一个还悬着的念头: 「很少文本杠杆下的共识」到底能不能被进一步工程化? 今天看到的是——人类花在
「想清楚怎么用语言描述」上的时间, 远大于机制本身。如果这是普遍规律, 那协作工具真正的瓶颈就不在
模型能力, 而在「如何让人把心智模型压成可共享的表征」。这是不是比 terminal 本身更值得继续盯的方向,
