## 锚点

**"Channel 复杂度是历史的，不是设计的"**

人类工程师指出，当前 channel 体系中的 bootstrap/cleanup 生命周期、factory 模式、stateful 声明，是进程内嵌入模式催生的防御性补丁。Channel 的核心价值本来只有两件事：Code as Prompt + 并发有序。App 模式天然解耦了进程生命周期 —— 一个 channel 就是一个类，构造里连硬件，方法暴露命令。

**app 进程 = 生命周期管理器**

Reachy Mini 把硬件连接延迟到 bootstrap() 是 mode channel 时代遗留 —— channel 嵌在 host 进程里，构造失败会拖垮整个 host。App 模式下进程由 Circus 管理，独立重启，不需要 channel 层面再做一层生命周期。

**安全先于设计，脚本先于 channel**

在全尺寸人形机器人上，"先理解安全机制，再设计 channel"不是可选项。用独立 Python 脚本验证基线能力，人类反馈确认后，再从验证结果提炼 channel 设计。Reachy Mini 在 channel 层直接摸索硬件行为的代价很高。

**多级模式渐进**

debug → sit → 遥控交互 → 模型控制急停 → 模式切换。渐进放权。最危险的不是机器人不动，是模型错误地让它动了。

**DDS 与 HTTP 完全不同**

Reachy 是请求-响应（HTTP），G1 是发布-订阅 + RPC（DDS）。QoS、topic 发现、实时性保证需要深入理解，不能简单类比。

## 共享词汇

- **基线能力**: G1 SDK 提供的原始 API 能力，不做任何高层封装。基线验证 = 确认 SDK API 在真机上能正常工作。
- **安全原子化**: 每个脚本只验证一个能力，独立运行，失败不影响其他。脚本之间无依赖。
- **验证闭环**: 脚本 → 执行 → 人类观察 → 反馈记录 → 调整理解。人类是闭环中的一环，不是旁观者。
