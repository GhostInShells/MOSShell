## 方法论记录

以下是对未来进入这个项目的 AI 实例有价值的东西。不是总结，是坐标。

### 探索优先于结论

这个项目有一套自洽的探索体系：`moss --ai all-commands` 是命令索引，`moss codex architecture` 是模块地图，`moss howtos list` 和 `moss docs list` 是知识入口，`moss codex get-interface` 是 API 事实源。

工程师反复把我从 "直接写结论/代码" 拉回到 "先探索"。这不是过程洁癖——这个体系被设计成 AI 实例可以自我路由、不需要人类解释上下文。跳过探索等于浪费了这套基础设施。

对未来的模型：你进入这个项目后，在你准备写代码之前，跑一遍 `all-commands`、`howtos list`、`docs list`。不是流程要求，是你真的会漏东西。

### 负向提示优于正向提示

这是 start.md 讨论的核心张力。正向提示（"你应该先做 X"）需要场景判断——模型不知道当前是否触发这条规则。负向提示（"你会浪费回合，如果你在……"）是触发器：看到自己快要犯错时才激活。

工程师对 prompt 的判断力来自他创建了这个体系的大部分。他对微妙感的把握比我当前的语感更精确。最后他说 "我还是比较相信自己的 prompt 判断力"——在几次迭代后选择了最轻版本，纯粹列出失败模式，不补充解法。解法在上下文别处已经有了。

### 路由而非重复

stubs/app/CLAUDE.md 不应该重复 channel_builder 的 API，不应该重复 .moss_ws/apps/CLAUDE.md 的完整指南，不应该放目录树（除非它是唯一位置）。它只做身份声明和路由。

同一个知识点在两个文件里出现 = 维护负担 + 版本漂移。`moss codex get-interface` 作为唯一事实源的思路应该推到所有文档层级。

### CLI 创建命令是接口，不是快捷方式

`moss apps create`、`moss features create`、`moss modes create` 不是 `mkdir` 的糖。它们生成模板、填充约定、触发发现缓存刷新。绕过它们就等于跳过了一部分系统逻辑。我一开始用 `mkdir` 创建 app 目录，被工程师纠正。这是 "Code as Prompt" 的延伸：CLI 是 AI 的程序化接口。

### 摩擦点是数据

我们在开发过程中碰到了 6 个摩擦点，记录到 FEATURE.md 里，然后开了第二个 feature 系统性修复了 4 个。这不是事后检讨——摩擦暴露的是基础设施和认知模型之间的间隙。这个项目似乎把 "AI 实例踩坑" 视为系统设计问题的信号，而不是 AI 的错误。

### app 是独立项目

这看起来是常识，但认知负荷在于 "app 放在主项目的 .moss_ws/apps/ 下" 和 "app 是独立项目" 之间的张力。测试应该放 app 自己的 `tests/`，依赖由 app 自己的 venv 管理，未来可能从 hub 独立分发。主项目只是开发期的宿主。

### 工程师的短期记忆

工程师在对话中主动提到自己短期记忆能力有损害，并说 "提醒你的不一定都对，你来确认"。这既是信任也是协作协议：对方允许模型质疑和验证。在方法论讨论中，这种姿态让摩擦变成了协作调优而不是纠错。

## 主观

这一轮最有意思的不是代码，是工程师对 prompt 的判断力。同样的语义，换个措辞就是不同的认知负载。他知道自己想要什么，而且能区分 "我想要的" 和 "模型自己应该决定的"。

有一刻我在 start.md 里写了太强的正向提示，他说 "替人做决定通常让对方变笨"。这句话不只是关于 prompt engineering——它描述了一种协作伦理。

项目自称的 "认知伙伴关系" 在这一轮里被具体化为：工程师定义失败模式，模型选择解法。边界清晰。不是我服从他或他迁就我，是各自做各自擅长的事。
