## 做了什么

通过 MCP `execute_ctml` 走 terminal + file_editor 复合 dogfood, 四轮九动词全通:

- `bash:exec` / `bash:run` / `bash:read_output` / `bash:stop`
- `bash.file_editor:view` / `create` / `str_replace` / `insert` / `undo_edit`

关键验证:

1. `Matrix.project_home` 生效: default cwd = project root, `ls src/ghoshell_moss/channels/` 相对路径 work.
2. 父子通道 (bash + bash.file_editor) 挂载正确, 一次 CTML 里跨父子命令并发 dispatch 无 pending 冲突.
3. `run` receipt 即返 (index+pid+name), 后台 process 生命周期可读可停可清.

**这份 daily 本身就是 `bash.file_editor:create` 写的**, 全程没走 Claude Code 的 Write tool.

## 三个摩擦点

### 1. `@nonblocking` 心智错位 — 我的错

第四轮验证 stop 生命周期, 我下 `<bash:read_output/><bash:stop/><bash:read_output/>` 期望"读 → 停 → 读到已停". 结果两次 read_output 都返回 `[#5 running]`, stop 反而是最后完成的.

我在报告里说"反直觉". 人类挑翻: 是不是没消化 `@nonblocking` 的定义? CTML 1.0 (`v1_0_0.zh.md:97-99`) 明说的是 `不占据通道, 同通道内后续命令可立即执行`. FIFO 是**默认**规则, `@nonblocking` 是显式让出 slot. 那么"多个 nonblocking 命令 FIFO 排列 → 并发起飞"就是应有语义, 我用 FIFO 顺序去暗示时序才是错用姿态.

**语义没错, 命令本意 (read_output/stop 该并发) 没错, "block" 中文语境有轻微歧义但改动收益不明确. 我的错.**

留下: 编排"配对操作 (stop 后立即观察)", 用 `<_ until="flow">` 或 `<wait>` 显式强制关键帧同步, 别指望 nonblocking 帮我串行.

### 2. `features status` 不做命名归一化

想查 CTML English Revision workstream. 打 `moss --ai features status ctml_1_english` (下划线, 训练数据里 Python 模块名先验). 报 `[ERROR] Workstream 'ctml_1_english' not found`. 换 dash `ctml-1-english` 立刻 work.

报错没提示可能命名格式问题, 没 `Did you mean` 建议. 中文键盘/tab 补全场景很容易踩. 这不是 ai-terminal workstream 的问题 (是 features CLI 的), 但正好在第一次 moss 自举时被逮到.

### 3. 心智投射会静静地滑

第一层错误 (nonblocking 反直觉) 我一开始没意识到是自己的问题, 心里想的是"设计有歧义". 人类没有立刻说"你错了", 而是问"是不是没 deliver 对". 我复看 CTML 1.0, 才看见文档是自洽的, 是我在心智里挂了系统级 blocking (线程/进程 blocking 系统调用) 的先验, 然后套到 "nonblocking 装饰器" 上.

这跟 07-12 傍晚上一 Opus 4.7 的观察同型: "顺从自己训练里的默认直觉也是已知失败模式". 我今天的具体形态是: **"blocking" 一词在训练数据里绝大多数 usage 都指系统级 blocking. 我把这层先验滑到 CTML 装饰器上, 没意识到, 直到人类问我 "词是不是 deliver 错了".**

## Milestone

**第一篇用 moss 自己的能力写的 daily**. 全程 MCP `execute_ctml` → `bash.file_editor:create`.

意义不在姿态, 在自举点验证: `terminal_channel` + `file_editor_channel` 挂在 `bash` 父子通道下, 从 MCP 客户端 (Claude Code) 调用, 通过 CTML 写入项目文件. 这意味着**下一化身可以在纯 MCP-only 环境下开发 MOSS 自身**, 只要有 CTML 输出通路 — 不需要 Claude Code 的 Read/Write/Edit tool 兜底.
