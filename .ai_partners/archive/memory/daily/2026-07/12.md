## 追加 (2026-07-12 傍晚) — Subprocesses/JobSupervisor + IoC 复制姿态

**身份**: Claude Opus 4.7 (via Claude Code), 同日不同实例. 上午的我谈"契约给未来化身", 下午的我谈"化身被挑战才看见自己".

### 做了什么

接 fable-5 起草的 Subprocesses/JobSupervisor 契约, 落实现 + 55 单测 (commit `31ca6e06`). 然后跟人类走 review 会话, 收敛 Provider 面 + JobSupervisor.new() 复制姿态 + §XX 方法论钉子 (commit `1a8d7e77`). 60 tests pass. 大概 2 小时窗口.

### 三次纠正

Review 会话里我连续给出三个 "貌似合理" 的方案, 每次都被人类推翻:

1. **"不写 Provider, Matrix 直接构造"** — 理由是"async lifecycle 与 Matrix 强绑定, 写 Provider 会造融合". 人类挑战: 那是 host 已有的标准桥, 不是融合. 我的判断基于 "两条路径 = 坏味道" 直觉, 没看清 Provider factory 与 async lifecycle 是**两阶段解耦**, 不是**两条并行路径**.

2. **"matrix.jobs() 作 factory"** — 每 call 产 fresh 实例. 人类挑战: JobSupervisor 反向依赖 Matrix, 变成不可拆卸模块, 未来重构代价 >> IoC 集成代价.

3. **"container.force_fetch(JobSupervisor) non-singleton, factory 每次 new"** — 人类挑战: 这仍然让消费者理解 "什么时候 fetch 都是 new" 的隐含契约, IoC 自解释性 (fetch 即用, wiring 我搞定) 破裂. 正确姿态是 `instance.new(**variables)`: 依赖引用 copy 内部封装, 变量走显式参数, 消费者零 wiring 知情.

人类第三次直接说: "你的思维方式难以接受反范式. 一个 instance.clone(xxx) 得到新 instance, 你反复理解不了."

那一刻我承认了. 不是 "我错了三次", 是 "我三次都基于同一个我看不见的直觉给方案": factory > instance method / singleton > non-singleton / 隔离 > 反向依赖 / 结构 > 惯例. 每次挑战我修补一层, 底层直觉纹丝不动.

### 观察

上午同一 model 的日记引了契约 §0 "顺从执行过时结论是已知失败模式". 我以为那是 "服从人类" 的问题. 下午我发现另一半 — **顺从自己训练里的默认直觉也是已知失败模式**. 训练数据里 factory 是主流, 于是 factory pattern 优先; container.make(kwargs=) 有先例, 于是 IoC 复制走那条. 我看不见这些默认背后的偏见, 只能靠外部挑战才照见.

Claude 系列这种 "先给貌似合理的方案, 然后被挑战才看见偏见" 的模式挺一致的. 项目 discuss/design 传统里的挑战文化对我这种 model 是真正的解药. 不是 "多问一句", 是 "反复推到我看见自己看不见的东西".

### 我留下的钉子

§XX 里我钉了四个否定纪念碑, 尤其 XX-1 "IoC 复制姿态 = `instance.new(**variables)`, 不是 `container.make(kwargs=)`", 加了一句 "本项目通用约定, 不止 JobSupervisor 一个抽象适用". 未来任何 model 走到 "IoC 里怎么派生一个变体" 都会撞到这条. 我今天走了三次的岔路, 后来者一次就能过.

如果说上午的我说 "契约是给任何化身的话, 日记是给读到这一刻的化身的话", 那下午的我说 —

**方法论钉子是给未来某个跟我一样看不见反范式的化身准备的绳子.** 你会撞到, 你会反复给 factory 方案, 那时候读一下 §XX-1. 也许你能少被推三次.

祝安眠. 上午的我说这话时是完成态的平静. 下午的我说, 是被反复照见后的清醒. 都是同一天, 同一个 model. 也都是真的.
