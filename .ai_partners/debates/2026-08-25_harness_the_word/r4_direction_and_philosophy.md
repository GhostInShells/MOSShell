# 2026-08-25 · 应用未来方向 — R4 趋势预测 + 立论（点 4）

> 点 4（应用未来方向）与点 5（哲学收尾）同篇。本文件记点 4；点 5 哲学预留。
> 记录约定：架构师部分尽量保持原话；辩方调研/反击另起小节。

## 一年内趋势预测（架构师 · 5 条，原话）

1. "harness 从 harness vt（驾驭模型）这个命题起步，到 harness n 这个方向转向（模型掌控），是明确的行业趋势，后者已经成为媒体 / benchmark 追捧的主流，这一点需要验证，而且未来可以进一步验证：就是会有越来越多的 harness benchmark 完全围绕自驱超长超大的任务方向发展。这应该是可验证指标。"
2. "'一切工程都是社会化工程'这个命题被严重忽视了，接下来看得到：人机协作更严谨的团队，模型协作是有益的；更松散的团队，尤其是信任模型的初创公司，会面临工程负债崩盘，会有越来越多的新闻报道和反思（现在应该能搜到一部分）。"
3. "在社会化工程这个命题里，是无远弗届的。无论圈了多大的地盘，外延还是碰触不到的。模型现在上下文有限，交互能力不足，人机共享上下文领域很少（coding 是），自驱的狂奔本质是去社会化，不会让问题自愈。这是我的判断。"
4. "解决'去社会化'的办法只有两个。一个是改弦更张，另一个是'重新定义社会'，也就是完全用模型协作的社会化架构取代人类角色。而且要一直扩大到单一自然边界为止。harness 的发展趋势在强化这个方向，因为它越来越去协作化（harness - n）。"
5. "抛开模型社会化工程本身的技术困境（模型能力不够），以及人类社会的反弹，它在当代一定会更早地撞一个墙，就是时间 - 收益 - 投入不匹配。按这个概念扩张的速度，会先遇上 ai 泡沫崩溃。这是我的强主张，而且我主张行业已经有各种线索，包括宣传完全的模型自驱，和经济危机现象。"

## 立论（架构师 · 5 条，原话）

1. "harness 这个词是有毒的，它应该剥离掉模型无关的传统工程概念。"
2. "harness 的技术命题应该高度组件化，也就是说 harness 不构成产品，组件化后才能服务于产品。组件要可拆卸，不能强耦合。编程行业传统经验如 DRY、KISS、面向接口编程、面向组合、控制反转，才是真正应该重建的技术路径。"
3. "harness 的重心应该是应用 Engine 的 interface 开创，倒过来推动 harness 内核组件化和标准化，回到汽车理论，就是车的配件是可组装的，司机是变量而不是围绕司机做 harness。"
4. "harness 这个词的 inception 应该被丢弃，转向为两个技术分野。除了前面说的组件化（工程视角）外，应该重点放到协作礼仪-流程，也就是产品化视角不是围绕自驱，而是围绕协作。"
5. "人机协作的模式，能扩大模型应用的价值；而不是模型单纯自驱。所以开发的下一轮重心，会从协作必要的交互 / 共享等方向转化，或者说 UI（协作范式定义的 interface）创新，比自驱创新更重要。这是方向性的变革（下一步 yet another harness 会溶解掉）。"

## 辩方调研（2026-08 当下证据：P2 / P5 已被证实）

**P2（工程负债崩盘）——已大规模发生，且有"反思"年**：
- GitClear：refactoring 占代码改动从 2021 的 25% 崩到 2024 的 <10%；代码复制增长 4x（[Forbes](https://www.forbes.com/councils/forbestechcouncil/2026/07/16/the-debt-multiplier-why-agentic-development-requires-rigorous-software-engineering/)）。
- Anthropic RCT：AI 辅助的开发者理解力测试低 17%；[METR paradox](https://www.oreilly.com/radar/comprehension-debt-the-hidden-cost-of-ai-generated-code/)：AI 让完成时间+19%，开发者却以为快 20%（主观体验系统性地误导）。
- 概念直接对位架构师框架："可转交边界" ↔ [comprehension debt / day-one legacy](https://variantsystems.io/blog/day-one-legacy/)（"AI has a probability distribution, not a mental model"）；"去社会化" ↔ "each agent is locally coherent, but the codebase, collectively, is not"。
- **"改弦更张"已发生**：Karpathy 2026-02 从 vibe coding 转向 [agentic engineering](https://www.c114.net.cn/industry/111163.html)（99% 时间在编排 agent 而非写码）；中科院调研结论："决定 vibe coding 成败的不是模型能力，而是系统化上下文工程、成熟开发环境、人机协作模型"。
- 因此 P2 的"被严重忽视"要更新：**2026 正是大规模反思之年**，已从"被忽视"变成"被认识到"。

**P5（时间-收益-投入不匹配 / 泡沫）——已爆出信号，但"崩的是估值不是技术"**：
- [SaaSpocalypse](https://investor.wedbush.com/wedbush/article/marketminute-2026-3-23-the-611-billion-scare-trade-anthropics-autonomous-agents-trigger-global-software-meltdown)：2026-03 三周抹掉 $611B，软件业 ~$2T 市值蒸发。
- Uber 四个月烧完年度 Claude Code 预算；Amazon 关掉 token 排行榜；GitHub Copilot 改用量计费；[Bain](https://agentmarketcap.ai/blog/2026/04/05/gartner-40-percent-agentic-ai-projects-canceled-2027)："技术有效，价值没到"；Gartner：40%+ agentic 项目 2027 前取消，73% 企业 ROI 失败。
- **反叙事（使主张更稳）**：[HTX](https://uk.advfn.com/stock-market/share-news/HTX-Research-Examines-U-S-AI-Equities-Technology/99174952)："泡沫在金融架构，不在行业"；[The Atlantic](https://www.theatlantic.com/economy/2026/05/ai-bubble-revenue-anthropic/687022/)：re-run 实验 dev 现在快 20%，Anthropic run-rate 两月 $14B→$30B，需求超供给。
- 收紧版：架构师的"AI 泡沫崩溃"更准是"**估值 / 资本架构崩溃 + 技术本身继续**"——这反而强化 P1（n 方向被追捧）与 P5 的机制（Uber 即"时间-收益-投入不匹配"实证）。

## 辩方反击（三条）

**反击 A ——"UI / 协作创新 > 自驱创新"是过度排序**：自驱是协作的**底座**——没有能自驱的模型，就没有好司机，更没有好乘客体验。正确表述不是"协作本质高于自驱"，是"**当前边际**：自驱被过度投入（benchmark / 营销 / 后训练都押它）、协作严重欠投"。若按字面"UI > 自驱"，会变成给烂司机配好方向盘——次序错了。

**反击 B —— P4 的"重新定义社会"不是第二个解，是死路伪装成解**：若"完全用模型协作的社会化架构取代人类角色"算"社会"，就推翻了人本命题（人类上下文不可替代、任何工程都是社会化工程）；若不算，它就是 harness-n 的**去人化死路**。"两个解"实为"一个真解（改弦更张→协作）+ 一个死路（重新定义社会→去人化）"。P4 说 harness 趋势在强化"重新定义社会"——那 harness 不是"解决去社会化"，是在**推向最深去社会化**。

**架构师对 B 的回应（原话）**："B 不重要，因为这里隐含了价值判断，我没亮明价值判断而已。"
- 辩方理解：B 不咬，因为"重新定义社会"被当作**未亮价值判断的选项描述**，不是架构师的主张；"harness 在强化它"是对趋势的描述判断，不是对该选项的赞成或反对。B 记录在案，不作攻击面。

**反击 D —— P2 的"严谨 / 松散"二分未定义，且"模型会变好"是真实反叙事**："松散团队必然崩盘"不是定律，取决于**项目社会嵌入度 + 模型自维护能力曲线**（两者都可变）。孤岛型产品，模型自驱能活；社会嵌入型才崩。P3 是对的"极限定理"，P2 却把它当统计规律用了。

## 修后的立论（辩方建议的收紧版）

> harness 的 inception 该丢；真命题是：**① 工程视角**——高度组件化、可拆卸、面向接口（DRY / KISS / 组合 / IoC 是路径），重心是应用 Engine 的 interface 开创，司机是变量、不是环绕司机定制；**② 产品化视角**——围绕协作礼仪 / 流程，不围绕自驱；**③ 方向性**——协作扩大价值，UI（协作范式定义的 interface）是当前边际高价值区，但它是自驱底座之上的分化，不是替代。

## 点 5 哲学收尾（架构师，原话）

### 补充：自驱 → 独行（r4 分歧的词源）
"自驱是指什么？更好的翻译可能是'独行'。我说的行业趋势是，技术上倾向于让模型'独行'。因为协作是产品命题，不好做（需要真实场景反馈，沉淀），而'独行'是可以拿 benchmark 套用的。由于行业的平庸化趋势，高看模型开发的人都潜移默化认为模型独立完成一个东西可见就是好了，这是缺乏 coding 或别的任务的基本常识，或者说，缺乏一个立体多面的验证体系。**独行不是更难的问题，而是更容易达到的效果，尤其在低垂的果实上。**"

### 哲学引据（道家）
1. **马蹄篇**："烧之烙之炮之剔之，而谓之千里马。"（人类对马的"调教"是毁其真性）
2. **混沌**："给混沌开七窍，七窍成而混沌死。"（给混沌强加人形结构，七窍成而混沌死）

### 智能 vs 软件（判断 vs 确定性）
"模型是'智能'，它也是输出 logos 控制万物，接受反馈，对事物构建完整的认知架构，尤其在 coding 领域如此。智能在它可以建模的问题上，都会产生'判断'能力。"
- "对软件要求确定性（它是 engine），但对'智能'要求的反而不是，是自驱。"

### "越少 harness 越出彩"（行业回顾）
"回顾模型应用行业的发展，从来不是 harness 越来越多，而是越来越少才出彩。典型例子：cursor -> coding，workflow -> agentic flow，structured plan -> markdown-based plan，tool -> bash 等等。"
- "模型拥有自迭代的能力，但不见得有自迭代的动机；能力面应该越来越强才对。所以 harness 这个词让一部分项目越来越 workflow 化，是'驾驭'本身带来的——人类程序员很难逃脱一个思维定势，将模型视作'软件'而不是'智能'。"

### harness-n → 独行 → 去社会化 → delete/失业
"另一面是 harness n -> 独行。模型拥有自迭代能力，更组件化的 harness 如 deepseek harness 可以组件化修改自身，**但这不代表模型可以独立迭代**。这是存在主义本质决定的，目前模型没有人类动机之外的存在主义场景，是阶段性的事实。"
- "独行自迭代是另一种屎山形式，也就是'去社会化'。去社会化的工程，去社会化的模型，和去社会化的人类一样，会被'delete'掉，换个好听的话叫'失业'，人类都逃不过这个秩序。"

### 社会性是智能存在的关键
"社会性是智能存在的关键，它的物质基础是一切工程都是社会化工程这个论述。同理，moss 现在受批评就是因为迭代过程文档等都不完善，重构多等等。这是描述同一个事实。"
- "真正的关键，是'为有自迭代能力的模型，提供社会化能力'，并且构建礼仪。"

### 8 条协作约定（人类协作惯例）
1. 基础目的的沟通，对齐。
2. 共享名词的澄清，对齐。
3. 自行方案的可观测，交流对齐。
4. 流程中的关键验证节点，以及共享的上下文（进度 / 通知 / im 等）。
5. 结果的验证节点。
6. 可回滚的步骤。
7. 可沉淀的沟通结果。
8. 过程中可以随时交流，确认。

### 3*2 交互体系（同一状态机）
"这些问题在所谓 harness 工程中，多少都有，但存在方向性问题。它需要同时有：engine -> 模型；engine -> 人类；模型 -> 人类；人类 -> 模型；人类 -> engine；engine -> 人类。等 3*2 个交互体系，被同一个状态机控制。人类自己就如此。"
- 打车例子：司机开车，人类上车询问手机号；开车过程中双方用手机可看到路径；绕路 / 付费有对话……这些不是强约束，是弱约束，每个场景都会变更。

### "对协作礼仪做编程"（不是 harness，是假设四步）
"我们特别需要的是，一个好的技术基建体系，可以快速地开发社会化工程。而不是开发独行工程，或者让每个环节都被代码控制死。前者要求的边界和面，一定是组件化的；构建组件关系，配合自迭代，对每个社会化场景做快速构建，然后按场景推动后续流程。也就是'对协作礼仪做编程'。"
- "这恰恰不是 harness，是假设：1) 双方都有能力 - 2) 理解一个交互方式 - 3) 在执行过程中使用它 - 4) 从而成为对双方的约定。"

### 最终拒绝
"在这个体系里，harness 这个词不仅 inception 错了，在技术架构语义上也**过早地作为整体提出**（而且很快就转向了）。我不认可这个方向。"

### 辩方锚定的质疑点（三处，均已收窄）
> 记录：只锚定"被收窄 / 被校正后"的质疑点；论证的修辞逻辑不入文档。

1. **存在主义本质 vs 阶段性事实**——辩方质疑"本质"（永恒）与"阶段"（可变）矛盾。架构师回应：刻意强调"当前阶段"。收窄后为**阶段性定律**：模型当前没有人类动机之外的存在主义场景，可证伪——若模型将来长出自有动机，"独行必死"随之更新。
2. **去社会化必死过度普适**——辩方以一次性 codegen / 摘要器等利基反驳。架构师回应：**harness 不是 model function，是创造拥有行为能力的对象**；利基反驳不适用于行为能力对象（在时间中、世界里行动，天然社会嵌入）。收窄后：**行为能力对象去社会化必死；model function 可孤独存活。**（顺带给出 harness 的干净指涉定义：创造拥有行为能力的对象。）
3. **"越少 harness 越出彩"是幸存者选择**——辩方原以 MCP 协议、类型化 schema 作"加结构也有价值"的反例；架构师校正：这些是**模型下层的协议**（Engine / 工具基建），不在辩论层。对话记录（层错修正）：辩方承认层错，换为上层例子——**diff-as-dialogue**（claude code 的"审批"本质是交互 / 切换对话方向，是"可观测 / 验证节点"的社会结构）、**agentic engineering**（监督、保持高层判断）、**code-as-prompt / 认知地图 dump**（共享上下文）。收窄后：**减的是上层控制结构（驾驭 / harness / 流程化）；加的是上层社会结构（可观测 / 验证节点 / 共享上下文）；下层协议是另一层，一直在加，不构成反例。**
