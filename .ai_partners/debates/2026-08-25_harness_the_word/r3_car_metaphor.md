# 2026-08-25 · harness 有效边界内的名词评价 — R3 汽车隐喻

> 本轮：第一个主张确认 + 汽车隐喻（为什么对）+ 乘客二分 + 挂账两处。
> 记录约定：架构师的比喻/论据尽量保留原文质感（不过度压缩）；辩方校准保留关键原话。

## 第一个主张（已确认）

**主张**：harness 作为一个"整体"（统一框架）是拓扑错位的——无法对 Engine 做好的抽象（仅借到完整 OS 抽象），所以作为框架无意义；实际是组件集合（permissions / agent / session / subagent / context-manager）被叫成统一框架；旗舰例（Claude Code）本质是闭源 Application。这个"整体"之名让造 Engine 的开发者处处撞拓扑错位、耦合太死。诚实的做法是拆成组件。

**辩方 review（已确认，且被公开证据加强）**：
- 行业确实把 harness 当整体：`Agent = Model + Harness` 跨厂商共识（Microsoft / LangChain / DeepSeek / Anthropic）。
- vt 烟枪：Anthropic 官方标题 "Harnessing Claude's Intelligence"——把模型的智能当 vt 对象。
- 最利主张的一条：[LangChain](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness) 定义 harness 为 "every piece of code, configuration, and execution logic that isn't the model itself"——**残余式（排除法）定义**，字面上就是"组件名词的代称"。行业自己最常引的定义，已默认 harness 没有正向统一身份。
- Engine 缺位是结构性的：标准组件清单（loop / context / tools / memory / permissions / subagent / hooks）里**没有领域 Engine 抽象组件**，工具全跑在 OS 上。
- 反向证据帮主张：[DeepSeek Harness](https://github.com/deepseek-ai/DeepSeek-Harness) "一切皆插件" / "[把 Agent 拆成零件，再还给开发者](https://zhuanlan.zhihu.com/p/2072721562197824697)"——最好工程本身是组件化的。

**结算（vt / n 分裂）**：
- **vt 用法**（harness the model）＝毒：把模型当被套对象。
- **n 用法 + 高度组件化（面向接口）**＝真技术命题（deepseek-harness 正确，非面向接口组件化存疑）。
- **n 用法 + 统一整体**＝残余袋 + 框架幻觉 + 拓扑错位。
- **概念可救（组件化名词），词不可救（马这个 image）**。杀词 vs 还读法落到"都不完全"——**换 image，保概念**。

## 懈怠（inception 的惰性）与"会安慰人的死罗盘"

架构师：
> "最大的问题是，这个 inception 在应用指向上，不承诺引擎的抽象，实际上把已有的引擎当成了全部，我认为是一种 inception 产生的懈怠（例子：bash is all you need 这个主张）。"

辩方校准（保留原话）：
> "阶段精确的镜子显示 'harness 内部已有一只完整 Engine（OS）'——这是真的。但镜子的完整是假总体：OS 是别人替你做好的一只 Engine，harness 自己的 Engine（GUI / 机器人 / data 域）没建。于是 inception 把'借到一只 Engine'换算成'引擎问题已了结'——这就是 bash-is-all-you-need 的心态。这比死罗盘更坏：死罗盘是不动（忽略它还能自己找路）；会安慰人的死罗盘是'指着你已在的地方说到了'，于是你不修通往 Engine 的路。"

## 汽车隐喻：为什么对（架构师主张 + 辩方 5/5）

架构师：
> "我认为 claude code 真实做的一直就不是 harness 这个隐喻，他们实际上一直做的就是汽车，但我不发明这种新名词。MOSS 拆了那么多 blueprint，完全是组件式的思想，但没有可装线的行业标准。所以我也期待那个标准，现在是被迫自己做总线。"

**架构师的理由**：
1. 模型在人机协作里不是"马"，是**驾驶员**（甚至不是 copilot）。claude code 的 engine 主要是 OS 体系，已有完整 os-engine 抽象面，且成协议标准。>"这个动力不是马带来的。很多嚼子套在了 os 上。"
2. 模型自己做 tasks、自己 plan，本质是 driver。多数人用 claude code / deepseek harness 不是 vibe coding，是**许愿式编程**（架构师自称边缘人群：自己定义详细步骤）。>"如果这个体系叫 harness，那么 Uber 滴滴的司机难道是马么？" 模型知识比许愿者更丰富（类似司机知道地图），降低乘客时间开销，让乘客做更多事，中间还能聊天。**司机的角色明显更合适。**
3. （挂账）harness 的 vt 隐藏了一个极其有毒的倾向——待展开。
4. 汽车是**工业级组件化环境，驾驶员是变量**；harness 不是——它是 per-horse 的实现（大了小了、高了矮了、长了短了、轻了重了），inception 里包含对模型的过耦合，实现也是如此。

**辩方评分（5/5 过杠）**：
1. Engine 一等格：汽车有引擎 → 过。
2. 模型不落动力/对象：模型=驾驶员 → 过。
3. 保组件化：汽车=工业级组件化环境 → 过。
4. 治懈怠：汽车把"平台 + 引擎舱（标准接口）+ 可换引擎"摆成一等未建方向，不让你以为已到 → 过（最强）。
5. 保缰绳面：方向盘（控制传导）+ 乘客-司机交流 → 过。

**映射**：驾驶员=模型 / 方向盘+传动=harness 的治理（输出+反馈）/ 引擎=OS / 驾驶环境=payload。由此：行业把整个车叫"harness"是错（那是 Application）；harness 若作组件只配当"方向盘/传动"。

**"驾驶员是变量"是最深的刀**：harness 是 per-horse（过耦合到具体模型）；汽车是工业标准平台，驾驶员可换。这把"面向接口的组件化"内建进隐喻：引擎舱=标准接口，引擎可换，驾驶员可换，只有平台是标准。与 MOSS 痛点直接对上（组件式思想有、可装线行业标准无、被迫自己做总线）。

**"人是乘客"反转**：标准 human-in-the-loop 把人当驾驶员、模型当工具。反转：**人是乘客（许愿、聊天、必要时抢方向盘），模型是驾驶员（自己 task / plan、知道地图）**。许愿式编程观察：多数人不是 vibe coding，是"给目的地，让司机开"。

## 乘客二分（架构师，新增）

汽车隐喻里，模型是乘客+司机中的**司机**，目的地是乘客定的。两种乘客：
1. **自己可以开车的乘客**：让模型驾驶，自己更轻松、有更多并行任务可做；有问题时可停下来自己做主驾；模型需要成长时，这个乘客还是"**驾校教练**"。
2. **自己不能开车的乘客**：依靠模型去目的地，双方做的是"**目的地校准**"。

## permission 四层（架构师主张 + 辩方校准）

架构师：
> "现在的 permission / approve 等概念都是错误的，它们真正做的，和乘客与司机的交流很类似，是交流和约定，技术上并不是强授权。只是人类拥有急停和门控，在这个阶段是必要的。**急停 - 门控 - 复查（授权）- 对话**是四层命题。我认为所有产品实际上都会落入我这个边界判断，不管他们意识到没有。"

辩方校准（保留原话）：
> "急停、门控是真执行（沙箱 / allowlist / deny-by-default 不是交流，是系统强制）；复查、对话是约定（模型提、人应，是乘客说'这站下'）。准确说不是 'permission 全错'，是'行业把四层全并成一个 authorization，把约定层误标成强授权，从而掩盖了司机在开车这个事实'。你的四层正是切开这个混层——它是对的。"

## 辩方反力（保留）：见习司机精度

> "汽车隐喻的'驾驶员'是方向，不是现状。当前模型是'见习司机 + 持刹车/门控的乘客'——你的四层之所以必要，正因为它不是正式司机。隐喻要连四层一起用，否则'驾驶员'这个 image 会过度许诺胜任力（真司机有执照、确定性；模型会幻觉）。四层是隐喻的内建部分，不是附录。"

## 有毒的点：驾驭范式 vs 协作范式（架构师展开 · 挂账#1）

### 范式区分
- **司机-乘客 = 协作范式**；**harness vt = 驾驭范式**。
- anthropic 启动 claude code 实际是驾驭范式（让模型帮程序员写代码）；早期架构不完整时，只是取代了人类复制模型代码的步骤——还是 **cursor（光标补完起点）和 copilot 思路**。
- claude code 真正体现价值时，已经不是 harness 而是协作范式——模型自己写代码，甚至长程执行复杂任务（**以天为单位**）。
- 象限：**左（模型完全自驱）· 中（协作）· 右（人类完全驾驭）**。实际产品结果是正态分布，**协作是主轴**。

### 协作的关键命题（5 个）
1. 共享能力
2. 共享认知地图
3. 共享状态变化
4. 共享结果
5. 可以移交方向盘

### 各命题的失败形态
- **不共享能力**：非程序员用 harness（出圈做法）让模型写红色警戒游戏，模型啪啪写完，好坏完全不知道 = 偏左形态，只有模型知道发生了什么；人类系好安全带，睡一觉就到了。
- **不共享认知范围**：人类看不到模型写的（Plan, tasks），无法理解往哪走。>架构师："我做 moss 比如当前 mindflow 重构、整个 moss start 体系，就是在把我的认知地图 dump 到模型可以理解。不共享认知范围是不可能协作的。" 模型自主调研项目**挂一漏万**、改动时快速收敛到当前理解 = 典型失败模式。反过来模型调度 1000 个 agent 并行干活，人类完全无掌控。
- **共享状态变化是关键**：claude code 的操作审批好——清楚看到 diff；>架构师："本质上不是 approve，是交互、切换对话方向。" **deepseek harness 掉坑**：一个简单 approve 动作，拒绝后模型立刻下一步，中间还 waterfall，给人类讯息是没排版的源码（可理解，赶进度）；代价是**拆掉了交互**，是单纯 harness（**reject 像勒嚼子，没有对话能力**）。
- **共享结果**：coding 场景经 IDE 实现；属于 harness 不提供 Engine 支持、靠别的软件。行业 application 靠这个吃饭（没意识到这本身是模型擅长的）。
- **不移交方向盘**：不能做真正人机分工。**harness 不是滑向最左，就是最右。**

### 行业噱头 = 最左
- "模型套上 harness（注意，不是 vt，是 **n** 了）就一骑绝尘完成交付"——benchmark / 营销 / 模型平台提示词 / 后训练都围绕这个命题（claude code 的提示词肯定要你少打扰）。
- 但导致 **1-5 全部崩盘**：人类大脑没有项目的虚拟机构建，无法推测问题位置；模型代码是"屎山"——**不是指质量**（比人类屎山好），是**"可转交边界"**。本质上项目在"去社会化"。（>架构师："这是模型初见批评 moss 文档少的 - 我的反驳是 code as prompt 就是最用心的文档，普通文档目前不紧急。"）
- **一旦出问题，又滑到最右。**

### 当前做好人机协作是必然（三条）
1. 任何工程都是**社会化工程**。
2. 外部世界交互基本在人类，人类上下文比模型大（**数以年计，不重置**）。
3. **协作优先级高于实现优先级**；协作要面向人类心智模型可读。

### 路径（解决两个问题）
1. **共享一切**。
2. 寻找**协作礼仪**的最佳实践，类似人类社会组织之间，落到产品。

### 行业现状 + 严重声明
- 行业不把精力做好 1+2，而是做了很复杂的**缰绳**，但人类用不了，从而放任模型行动。为更好 benchmark，模型后训练走向"**平庸化**"（快速交付给普通人、让大家感觉良好）。
- >架构师："harness 这个 inception 的隐喻是**人类完全主导**，但人类没能力主导时，相当于给了马一鞭子，然后闭上眼。用一句话形容'**盲人骑瞎马，夜半临深池**'。下半年对 harness 的反思会越来越多。这就是我为什么说 harness 这个词有毒。"

## 辩方 review：毒性在词还是激励（挂账#1 的回应）

### 承重（辩方认的四条）
1. **驾驭 vs 协作范式分裂** —— 这是挂账#1 的答案核心：harness vt 的毒性就是"它是驾驭范式，而现实是协作范式"。它同时解释了 claude code 的价值拐点（从复制代码到长程自驱协作）与"n 用法反而合理"（组件化名词不承载 vt 的驾驭动作）。
2. **deepseek-harness 掉坑案例**（reject 像勒嚼子、无对话）——具体、可检验，是"拆掉交互 = 纯 harness"的实证。
3. **"屎山 = 可转交边界"** —— 对 code quality 的真重定义：软件是社会性工件，不能社会化转交就是负债。"任何工程都是社会化工程"是这段最硬的一条。
4. **盲人骑瞎马，夜半临深池** —— "人类完全主导"的隐喻 + "人类没能力主导"的现实，一句钉死。

### 反力（三条）
1. **毒性在词，还是行业激励结构？** 最左噱头由 **benchmark / 营销 / 模型平台提示词 / 后训练** 共同推起——这是**模型厂商的经济结构**，与"harness 这个词"无直接关系。"harness 有毒"在 **inception 层对**（隐喻确实是驾驭），但**让 1-5 崩盘的执行者是激励结构**，词只是命名/强化它的那层。后果：**改名治不了根**；"下半年对 harness 的反思"真正该反思的是激励，不是词。
2. **1-5 崩盘是激励后果，不是象限定律**。一个设计良好的"最左"agent 完全可以共享能力/认知地图/状态/结果、移交方向盘——它只是被"别打扰人、benchmark 快"的激励**禁止了共享**。修法不是"避最左"，是"**最左也要强制共享**"——自治与共享不是互斥，是激励把它们对立了。
3. **中间是真实的，但是不稳定的**。协作（主轴）是**脆弱吸引子**：人机无真正问责、上下文量级差巨大（人以年计不重置），所以协作要靠"协作礼仪"工程**维持**，不是天然稳态。这正是架构师路径 2，也是**最难、最没人建**的部分。行业做复杂缰绳而不做礼仪，**因为缰绳易、礼仪难**。

### 可检验命题（辩方标记）
- **"驾驭范式双稳态（非左即右）"**：控制范式要么过控（右：人微操）、要么失控（左：人跟不上），**协作是第三态（共享驾驶），驾驭范式表达不出来**。辩方认，但这是强断言，值得以后拿具体 harness 设计证伪。
