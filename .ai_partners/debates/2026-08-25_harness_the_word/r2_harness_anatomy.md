# 2026-08-25 · harness 的技术实体 — R2 庖丁解牛（架构师框架）

> 本文件保留架构师对 harness 的技术实体展开（11 范畴）。这是"技术实体"阶段 —— 按方法论先于此完成；inception 问题随后再落。架构师框架原话以 `>` 锚定，辩方只做验证 + 两点补充 + 两级结构分析。

## 方法论补正（架构师）

真问题分两层：**inception**（名字种的动机 / 未来方向）与 **技术实体**（这个东西总该有个名字）。方法：先把技术实体庖丁解牛；当 inception 不成立时才回到"这东西总得有个名字"；把技术实体聊完，inception 问题更突出。**先技术实体，后 inception**。

## harness 的技术组件化（架构师 · 11 范畴）

1. **payload** —— 真正被操作的对象。对 coding agent 而言就是代码本身；围绕它有一整套系统（git 配套、worktree、分析工具…），都围绕 payload。
2. **动力的传导** —— 系统级工具面（bash 等）。用 MOSS 自己的话说：把 logos（token 的语义别称）转化为 action。
3. **动力的来源** —— 实际上是 runtime。bash 工具的 runtime 是 bash，有的是 python、ts 等。
   > 架构师："这里标记了 harness 的第一个关键技术错位——模型提供动力吗？行业专有名词 Engine 本身就描述了各种提供动力的系统，或更直白一点，它就是 os 里的 s — system。这是 harness 的范畴内。"
4. **操作界面** —— 让模型/人类理解可操作对象。以 claude code 为例，技术表面只有 command，真正的工具集和上下文在模型侧。衍伸两个操作表面：
   - 面向模型的 interface：tool use / skill / memory…
   - 面向人类的 interface：tui / gui。
   > 架构师："我认为 harness 原本定义的应该是前者（面向模型的 interface：上下文/工具的组装）。但这个外延明显拆不出来——人类 interface 里要负责 mcp / 工具的连接等。我把 skill 也认为是操作表面。渐进式披露这个词我觉得很奇葩——人类的 GUI 从来都是折叠的，也没见过发明'渐进式披露'这种概念。"
5. **连续行动（loop）** —— 什么时候该停、该走，是 harness 的关键。claude code 常在想停时多发一个 notification 硬要多答一轮。**plan / tasks 是 harness 目前最有特征化的部分，还在延伸。这是自驱的部分。**
6. **人类交互** —— harness 非常关键的组件：审批、diff、dialog 问答。
   > 架构师："这就是我说你讲的'挽具'并没有消解问题。UI 这一层去形态化，讲的是如何交互。键盘/窗口/触屏/语音是不同 UI 大分类（输入/输出层）；另一类是交互范式——回合制、阻塞式（alert 弹窗）、双工（聊天室）、多通道。harness 实际上把这一层做到了内核。所以不能声称这一层不是 harness——它对应的形象自然不是挽具，而是缰绳。"
7. **工程能力的组合集成** —— 工具注册、运行时通讯（mcp 等）、组件能力（dsh 的 plugin）、各种 hook、各种协议（ACP/MCP…）。这是"套马"里"套"的动作机制。
8. **自我迭代与改进** —— 运行时修改一些东西对以后有影响。典型：claude code 的 memory。有的系统不放大模块，而是把它工具化。
9. **上下文治理** —— 各种组件集成后，映射出的上下文做良好治理。复杂在：可编排、组件化、工具化、可拆卸、上下文缓存机制、压缩时机点、超量限制、compact 机制、过量上下文转存文件等防爆机制；还包括上下文的存储、回滚、分叉。
10. **异常管理与自愈** —— 检测、故障感知、异常不中断循环、不永死。
11. **可配置化体系**。

## 辩方验证

**回答架构师"算不算主流 harness"**：算。这 11 范畴基本覆盖主流 agent harness 的 scope，无重大缺失。（**辩方注**：此断言未对照任何具体主流实现清单，"覆盖主流 scope"是无基准比较。待证。见 R2.6。）两点补充——

- **同音异义**：这 11 范畴解剖的是 **agent harness（应用/运行）**。同名的 **eval harness（评测台，lm-eval-harness 那一支）** 是另一个较小、精确的另一层含义，本解剖未覆盖。inception 批判时这个 homonym 要留神。
- **略显未拆**：(a) 模型的推理/scratchpad/工作状态（部分落在 5）；(b) 并行 / subagent 并发（5/2）；(c) 真正的 system prompt / 指令组装（4/9）。

**点 3 + 点 6 合起来揭示的两级控制结构**（本解剖最有分量的产出）：

> **辩方注**："合起来揭示"与"最有分量"是辩方叙述层，非事实层。四角色 schema（runtime=马 / model=决策传导 / human=顶层驾驶者 / payload=货物）是**辩方对架构师点 3 + 6 的解读层，不是架构师原话**；"中间驾驶者"一词亦为辩方补充。架构师原话只给了两件事：点 3（模型不提供动力，engine/runtime 是动力源）、点 6（人类交互层 = 缰绳在内核）。本 schema 未获架构师确认，作为**辩方假设层**保留。见 R2.6。

> runtime = 拉车的力量源（马）；model = 决策传导层（驱动 runtime）；human = 持缰的顶层驾驶者（审批 / 中断 → 驾驭 model）；payload（代码）= 被拉的货物。

所以 model **既不是马，也不是顶层驾驶者** —— 它是一个被人类缰绳驾驭、又驱动 runtime 之力的**中间驾驶者**。harness 作为"整个"的名字，把 model 在控制层级里错放了：它说"model 是被套的"，其实 model 是中间驾驶者（上被 human 缰绳、下驱 runtime）。

**留给 inception 的张力**（不在此判）：若 harness 的内核真把人类中途驾驭（缰绳 / 审批门）做进去，那**这层是好的**（安全、问责、能叫停失控）。所以反对"它控制"不成立——控制（缰绳）值得要。反对必须是更精确的：**是让"控制"成为整个系统的身份中心**，而非"控制作为一个部件"。这回到 whole vs component 分叉，也正是"技术实体谈完、inception 更突出"的落点。

## R2.5 · inception 判据收束 + 注意力分形（架构师）

> 本段是"定义真问题"层的收束。架构师明确以下论述重要，保留。

**判据终形（架构师）**：重要的不是"有一个新名字"，是这个新名字是否承载了**有效的边界保护**——名字的隐喻和边界要清晰、不漂移。
> 架构师："Laravel 取名就很漂移，他们的 DOM 取名叫 Eloquent。不管理它是当年最好的 DOM，后代的 DOM 都借鉴它的设计。（所以）名字好坏 ≠ 东西好坏。harness 的问题在于提出时就包含了传统工程命题，它的隐喻和边界不清晰。"

**注意力治理是分形动作（架构师，认为重要）**：
> 架构师："人类大脑内治理注意力、对外部治理注意力（桌面摆什么照片、书柜摆什么书、电脑放哪些应用、哪些通知放出来），仍是同一个问题的不同层面。注意力治理除 transformer 架构里的治理，延伸到外部世界也成立：渐进式披露 / compact 过滤 / plan-task / notification / 抢占逻辑，都是'外部'注意力治理手段。即便这一代外部治理都沉淀到内部（模型支持连续 session、gb→tb 上下文仍自洽），仍有外部边界的注意力——社会协作的注意力命题。"

**辩方校正（一处误读，记下避免复发）**：架构师点名 Matrix/Operator"可质疑"，是"批判尺度可适用于 MOSS"的转述，**不是自我批判**——架构师会对它们另有 argue，不展开。辩方撤回对 Matrix/Operator 的预判，改持"待辩论"。**批判尺度普遍适用本身**是方法论收获。

**辩方判断（两件事，非纯认同）**：
- **分形 ≠ 容器**：注意力治理是"同一命题跨尺度重现"（内 transformer / 外工具 / 社会协作），由一个命题统一，边界 coherent；harness 是"不相关的多命题塞一袋"（上下文治理 + IoC/DI/config），无统一命题 → 边界 arbitrary。（**辩方注**："统一命题"机制是辩方对架构师"边界保护"判据的引申，**非架构师原判据**；"注意力治理合格 / harness 不合格"是辩方超前判定，本节不作定论，下节再核。见 R2.6。）
- **对"transient"的让步**：内部上下文补偿（token 预算管理）会随模型变强而消退；但注意力作为**一般命题**不会消退——社会协作注意力的外部边界仍在。所以"注意力治理"不是纯 transient。
