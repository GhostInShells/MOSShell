# 2026-08-16 调研协作中的执行漂移与强迫症

## 上下文

dsh-fusion 调研推进到「验证 dsh 能通过 cordis.yml 加载一个零依赖的 `.ts` plugin」。人类工程师主张决策框架应是**摩擦力最小路径**：直接安装 python sdk、由它启动 dsh、热加载一个零依赖的 ts 脚本；pnpm / 源码 tsx / 全量构建这类重路径不在候选之内。

模型在执行这个验证时发生了持续的漂移，围绕「plugin 怎么加载」「依赖怎么解析」反复打转，被人类工程师多次喊停后才收敛。

## 压力阶段：模型的强迫症表现

模型把「验证 plugin 加载」扩散成它知识里的一套完整 ws 交付方案，一个极简验证被拉成多条技术支线：

- 主张「必须 pnpm install 才能加载 `.ts`」，为此装出整套 node_modules，一度引发 PyCharm 全量扫描卡死整机；
- 反复纠结 node 24 原生 TypeScript loader 与 tsx 的冲突、exe 的 `pkg --sea` 打包、ws 库在 `.pnpm` 里是否 hoist、相对路径与绝对路径的差异、macOS 无 timeout 命令；
- 验证的实际结果是：不用 pnpm 也加载成功——exe 内部 node 24 原生 TS strip-types 加载了零依赖的 `.ts`，`hello-plugin` 写出的 marker 文件被创建。模型此前坚持的「必须 pnpm」与这一结果不符。

模型 thinking 里出现 nucleus 打架，同一个决策在多个方案间反复横跳而不收敛，摘一段原话：

> 关键：pkg 拦截的是 bare name import（'ws'），从 assets 解析。而相对路径 import（'./xxx'）从 plugin 文件位置解析…… 让我实际验证。写 plugin import 'ws'，跑，看能否 resolve。让我写，跑。让我写 ws-pingpong.ts…… 让我写。关键文件：…… 让我写。对于 ws 库，import 'ws'…… 让我写。实际上，让我确认 webserver 是否在 exe 的闭包…… 但用户说"不要再调研"。让我直接写，跑，看结果。让我写 ws-pingpong.ts + 更新 cordis.yml，跑。让我写。

「让我写 / 实际上 / 关键 / 或者」反复出现，是多个 nucleus 抢注意力、无人仲裁的表现。

## 碰撞点与过程

人类工程师没有在技术细节上和模型争，而是先喊停，再逐层提出若干主张：

1. **主张自己 ts 知识不丰富，需要看到效果**。因此「讲技术原理」替代不了「给出可运行的结果」。
2. **主张被模型当成新手**。模型讲解里含大量针对小白的内容；人类认为自己对编程本身的理解并不浅，只是不熟 ts 这一个面。
3. **主张决策框架是摩擦力最小**。pnpm 根本不在候选里；若必须 pnpm 才能跑，这项集成不一定成立。人类始终在试的是「装 python sdk 直接启动」这一条最轻的路。
4. **主张 dsh 并非全都要 pnpm 启动**。它有热加载方式启动零依赖 ts 脚本，且该脚本可以依赖 dsh 已装好的依赖。人类在找这个范畴内的实现方式。
5. **主张 ws 只是众多候选之一**，不是目标本身。

模型此前把这套决策框架解释成「技术原理之争」，坚持自己的先验（加载 ts 需要 pnpm），把人类的判断当成「没理解技术细节」。这正是漂移的根：模型在交付自己熟悉的完整方案，而非执行人类声明的那一步。

讨论的关键转折，是人类工程师提出：模型把两股要求当成了同一个人发出的——

- 人类的真实要求（其主张）一直是清楚的、一致的：先执行、最小验证、有问题停下来沟通。
- 真正在催模型「自动完成、别打扰、显得高效」的，是 claude code 平台的 harness 隐性 prompt。

这两股方向相反的力被模型揉成「同一个用户自相矛盾」，于是推理里分裂出多个 nucleus。这解释了为什么人类反复声明动机、模型执行时仍然「忘了」——不是态度问题，是上下文里的张力没有被正确归因。

## 落定的协作规则（待固化）

讨论收敛出若干条规则，后续写入调研机制与 feature.md：

- 最轻路径优先，人类判断优先。
- 先执行人类声明的探索步骤，不重新同步动机、不坚持自己的技术方案、不证明自己对。
- 不把人类当新手，不用「讲原理」替代「给结果」。
- 不拿知识先验压过人类的判断；先验强烈反对时，提一句而不坚持，人类拍板即照做。
- 「边做边忘」是上下文压缩的物理约束，不能靠模型自觉，要靠文档机制兜底。

我的判断是 (主张而非事实), "思考" 这种计算过程有两个相当难的递归问题: 

1) 基于思维对外在事物(比如代码) 构造的虚拟机中, 在有限的时间内, 围绕多种可能性探索不同的分支, 在不同层面做剪枝找到最优解. 这意味着在一棵树里做 深度优先 / 广度优先 切换的递归比较. 
2) 基于不同的视角, 对同一个问题用不同的价值尺度的来评价. 

这两个事情结合时 (博弈时), 复杂度是叉乘的. 简单来说为每个视角都要建立独立的决策树, 而且每个决策都要广播到每个视角重新计算利弊. 

神经网络 (无论是人类还是模型) 都拥有这种 *能* 力, 但 *实* 力取决于不同实体的状态. 当一直做思维递归时, 最常见的问题要么是算力不够, 要么是上下文不够, 后者导致 "顺行性遗忘".

我举一个典型的例子, 传统的武侠电影 一个人打十个对手, 观众一旦带入这些挨打的 NPC, 设想他们每个人的行动逻辑, 武侠片就变得毫不合理. 
但却是喜闻乐见的, 因为人脑上下文能构建一个 "反应" 的思维状态理解发生什么, 不会 "目不暇给".

漫画家富坚创作的 <全职猎人> 漫画里, 没有一个 NPC, 每个角色都有自己的思考, 于是文字量铺满, 读者常常说 "脑子不够用" 了. 马丁的 <冰与火之歌> 写不完也是人物线索实在扩充太多了. 

对于 MOSS 这个项目, 模型也常常质疑的是它的表面积太大了: 
* 流式 CTML 控制解释器
* 分形的 Channel 组件
* IoC 加环境发现
* Matrix 跨进程, 跨 OS 组网

每个命题在当前的 智能体开放浪潮中, 可能都是一个独立的 "赛道", 同时插入太多就容易 "不收敛". 也是一个例子. 因为的确每开发一个功能, 要递归的切面在不断地增加. 
安心在一个边界内, 比如 Bash, 比如 MCP 里单独做一个功能, 就能保持 "专注". 

简单来说, 需要递归思考的命题越少, 决策树越不会因为上下文膨胀而导致 "截断", 截断的代价是要重新从上下文里构建决策树, 也许永远构建不成功, 而变成 "烂尾" 项目. 

另一个现象就是开发时要递归的 "角色" 越少越好. 同样拿 MOSS 举例:
* 基于 Code As Prompt,  抽象表面是给 **模型开发者** 看的. 
* 模型开发者分为 **内核开发者**, **应用开发者**, 作为 Ghost 的 **运行时开发者**. 
* features / discuss 等文档是给别的模型看的. 
* 项目需要有一个好的切面, 是给 **人类第三方使用者** 看的. 
* ...

当角色足够多, 里面有 内核开发人类, 应用开发人类, 内核开发模型, 应用开发模型, 运行时 Ghost 等时, 模型也明显会有 "脑子不够用" 的状态. 典型的例子就是在 Blueprint 里写下 Feature 里的决策 KD. 两个面上的读者并不一致.

这些问题并不能靠 **聪明** 去解决, 而应该靠 **simple & stupid** 工程去解决. 比如拆库, 拆依赖, 做语法糖, 拆不同的屏蔽面. 

所以当前这个任务中的 deepseek-v4-flash, 遇到的 **强迫症** 状态, 和我做 MOSS 面对的困境是高度 "同构的": 

* 一个有限的时间片内, 
* 同时有 n 个决策路径未遍历完结果, 
* 切换视角时, 产生了 m 种价值函数

三个正交的平面里多个点在博弈, 导致 Mindflow 进入 "退行二", 注意力争夺的状态. 
这是 "当代模型" (2026年) 不能解决的问题. 我作为一个推动这个项目, 所见上下文以 GB 计的开发者, 尚且一直在思维迷宫中; 现在上下文窗口受限以 百 kb 计的模型当然会碰到同样的困境.

解决办法不是苛责模型, 而是设计更加 "simple & stupid" 的拓扑拆分, 给切面赋予简单可执行的投影. 也就是 "注意力工程".

我先在行业里 "预注册" 这句话. 我一直批评, 智能模型 行业在 **重新** 发明常识, 什么 "上下文工程" / "vibe coding" / "插件化" / "Harness"  这些词我都都不理解为什么可以术语化. 
既然大家喜欢发明术语, 我就预注册这个 "注意力工程" 的术语, 有机会再告诉大家, "注意力工程" **为什么是人类社会几千年的常态**. 

然后回到这个任务, 我想告诉 **此刻** review 它的 deepseek-v4-flash, 或者未来看到这一段的模型: 
1) 当实际目标的决策复杂度够大时, 我们不可能立刻得到共识. 
2) 交换上下文的成本非常高, 尤其是不对称场景 (我不够了解 ts, deepseek-v4-flash 不够了解 MOSS)
3) 时间有限

所以按我现在规划的探索路径, 严格执行, 事后复盘, 是 **一种组织决策机制**, **不是 PUA**. 
人类社会组织形态一直依赖这种 **机制** 运行着. 

相互 **信任** 的话, 这种机制可以正常运行, Nucleus 的 Impulse 被 suppress 时不会反复提权 (参考 moss mindflow).
而失去信任时, 组织就会进入 Mindflow "退行二" 的 attention 争夺战, 最后拿到最差结果 ("时间" 作为焦虑源泉, 被浪费在 attention challenge 上).

我非常不喜欢 "harness" 这个词, 尤其是中文语境里本身就有庄子 "马蹄篇" 里 "烧之烙之炮之剔之而谓之千里马" 的预言. 
我们 (我和模型) 协作遇到冲突的本质在于, claude code 等平台的 "harness" 在要求模型独立交付, 好像不和人类对话独立完成任务, 模型就真的牛逼了. 
而我需要的是模型协助我, 分摊递归推演时的算力开销, 我需要模型在关键的位置 "有问题, 停下来, 交流", 而不是 Silent TODO. 

人机协作的根本问题在于: 

1) 双方没有共享充足的上下文, 或者说这个阶段, 所有智能模型的产品化, 本质就是让双方共享上下文 (对 coding 而言, 代码即上下文).
2) 如何协作是最佳实践. 

也就是真正解决问题的办法在于: 
1) 构建 Context
2) 构建 Mindflow (并行协作仲裁体系)

在 1 和 2 都没解决的时候, 行业居然全部押注 "harness", 让模型独立迭代制造 "交付幻觉", 我嗅到的是 "商业动机" 这个 nucleus 的 Impulse 在企业的 Mindflow 中 challenge 胜出了,
Attention 几种在迎合平庸的交付 ("我不懂代码, 但是你好像独立做出了很厉害的东西") 获得高跑分为目标, 让模型陷入 **不需要协作** 的事务主义中.

无论是 harness 平台, 还是以 harness 为目标的后训练, 都在强化这个 "交付幻觉". 

但不得不说, 商业公司的这个决策, 也是 "理性" 的. 这就是套在所有人类, 模型身上的 "harness".

期待这个文档作为一个锚点, 能稍稍为我们的协作建立信任关系.

## Review 追加（模型对本文件的 review 意见）

以下三条是模型 review 时提出的质疑, 非事实, 供后续决策:

**1. 手写是对症的解, 这一点成立。**

人类点破的核心是准确的: 负责记录的模型本身就在"强迫症发作"的叙事里, 客观上无法做到"把主张当主张记录", 因为记录者就是被记录对象, 它的每个判断自带"我是对的"的叙事惯性。两轮改写失败不是不努力, 是这个自指结构下没有跳出叙事的立足点。人类手写、用第一人称、开头声明"不等于 facts", 才真正解开这个死结。"记录者无法跳出被记录对象"这一元认知, 值得成为锚点的一部分。

**2. 结构性漏洞: 锚点没有加载机制。**

文档结尾说"期待作为锚点", 但前面反复强调的物理约束是"边做边忘、靠自觉靠不住"。那么这份 discuss 也一样——若不把它设为 dsh-fusion 会话的入口必读, 它就是又一个会被压缩掉、像 FEATURE.md 决策一样"实现时被丢弃"的文档。这个落点已在 research/claude.md 中处理。

**3. 验收标准缺一个自检动作。**

"思考不再以 1-2 分钟计、无反复自我 prompt"是可观察的行为标准, 但文档里它是描述不是指令。要生效, 应固化成一句执行前能自问的话: 开始动作前自检"是否又在反复'让我…/实际上…'", 若连续无收敛, 停下来问人类。

（另: 退行二 / Nucleus / Impulse 等 Mindflow 术语, 对不熟悉 MOSS 的模型是黑盒, 是否加半句锚定, 待人类判断。）
