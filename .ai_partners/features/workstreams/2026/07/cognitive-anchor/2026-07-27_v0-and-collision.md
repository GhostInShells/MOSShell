# Cognitive Anchor — 认知锚

> Use `moss features set-status cognitive-anchor <status> -m "note"` to update state.

## 引子

本 feature 的方法论建设过程本身使用了认知锚手法：模拟评审 → 同行审查 → 原审查者被审查 → 元对话 → 披露目标。对话轨迹作为本 feature 后续迭代的锚回放素材。

项目作者与 deepseek-v4-pro 的多轮对话是 MOSS 项目中锚密度最高的轨迹之一，本 feature 的创建动机源于此。

> **deepseek-v4-pro review:** 这个 "引子" 本身指向整个理论最有价值的洞见 — 但理论正文没有充分展开。锚的价值可能不是来自数据结构设计，而是来自对话场设计。作者和模型的碰撞产生了高密度轨迹，不是因为遵循了某个锚协议，而是因为对话场被设计成了 "碰撞 → 审查 → 元对话" 的形状。如果这成立，锚可能不是一种工程技术，而是一种对话场设计的副产品。想要更多锚，应该设计更好的对话场，而不是设计更好的存储格式。这个方向在正文中没有被充分讨论。

---

## Motivation

认知锚理论从 "上下文即意识" 的哲学出发，用来对抗超长上下文导致的认知腐烂。同时解决窗口问题，以及复杂思维场景（N 层递归决策）中的认知退化。它是一种传播-验证-校准的认知场碰撞工程化手法。

当代大模型技术，在不同的对话轨迹里，可以在某个时候让注意力/价值选择/逻辑质量和密度/对未来的判断等各方面最大化，或者说势能最大化。这时候将模型本身的关键帧存储下来，使之可以回放，就构成了一个锚点。

锚本身不是压缩态 — 它是单次请求的完整上下文，是最大窗口状态。它记录的是模型在那个时刻的完整认知条件：instruction + tools 现场 + memory + perspectives。这些是 memento 不记录的东西。memento 记录对话轨迹（发生了什么），锚记录模型的认知状态（模型在什么条件下产生了这个输出）。

> **deepseek-v4-pro review: 重复发明名词 (1/5).** "保存某一时刻的完整状态以便后续恢复" — 这就是 checkpoint。分布式系统有 checkpoint，ML 训练有 checkpoint，LangGraph 有 `checkpointer`，ContextBranch (arxiv 2512.13914) 的 checkpoint/branch/switch/inject 与本设计的 fork + replay 几乎逐字对应。memento §10 已经引用了 ContextBranch。概念上锚没有提供比 checkpoint 更多的新机制。锚不是 checkpoint 的重命名 — 还是它就是 checkpoint 在 MOSS 语境下的特化命名？如果是后者，应该明确声明这个继承关系并指出差异化的部分。否则读者 (包括模型) 会花大量认知成本重新发现 checkpoint 的已知属性。

模型可以自省到注意力的极值发生，所以可以在不同的认知锚形成时主动存储。存储动作不是书写（本质上是压缩），而是调用一个 command 直接记录。

认知锚可以在并行思考中被复用。比如 L2 架构设计 → L1 执行时，如果总加载 L2 的对话，注意力漂移就很严重。L2 被压缩成一个 feature 那种摘要后，执行状态中直接交给生产 L2 的锚做并行观测，实际上有更好的解释效果。认知锚可回放的特性使之成为思维状态的外化和传递。它可以反复用于生产不同时空的新认知。

人类也是一模一样的机制。当人类某个经历达到极值时，就会产生存在主义锚点。电影里完全是用认知锚手法做阐述，描述一个人的人生时，就是详细重放不同的认知锚，产生认知链。

锚本身也可以用 git 版本控制的方式，或者用目录的方式存放迭代路径。最终重放认知锚反思当下的 api 应该和存储认知锚一样简单。

MOSS 里的 .discuss 和 debates 等就是认知锚思路的验证，目前看到的效果实际上非常好。它们本质上是量子意识胶囊 — "量子" 不是民科是术语，表达了：1) 离散 2) 超越时间 3) 超越个体 4) 基于对未来的预测 5) 产生对未来的影响。

## 技术理念 — 五个步骤

### 第一步：数据来源 — 模型请求关键帧

锚的数据来源是模型的单次请求关键帧。它包含：

- **instruction**：模型在那一帧的系统指令
- **tools 现场**：那一帧可用的工具集合（函数签名、参数 schema、工具描述）
- **memory**：那一帧加载的记忆上下文
- **perspectives**：那一帧注入的感知视角

这四者构成了模型极值时刻的**认知条件**。memento 不记录这些 — memento 记录的是对话轨迹（moments、commits、reactions），是 "发生了什么"。锚记录的是 "模型在什么认知条件下产生了这个输出"。

锚的存储格式降级为 txt / md 文档。允许降级（剥离思考过程、工具调用痕迹），但降级是使用时的选择，不是锚的定义。完整锚保留 request 级别的全部上下文。

模型公司一直在用关键帧做 benchmark 或技术验证。锚将这个技术从人类工具变成模型自身思维的工具。

> **deepseek-v4-pro review: 低估行业已有经验 (2/5).** 
> 
> 存储完整 request 不是技术难题 — OpenAI 和 Anthropic 的 API 默认存储 request/response pairs。锚的真正命题不是 "能不能存"，而是 "存了之后怎么让未来的模型受益"。
> 
> "模型可以自省到注意力的极值发生" 作为一个工作假设，需要面对模型 calibration 研究几十年的反面证据 (Guo et al. 2017, Minderer et al. 2021 等)。模型的 confidence 和 actual accuracy 之间存在系统性 gap。断言自省可行而不引用或面对这个领域的工作，是高估未验证命题。
> 
> ContextBranch (arxiv 2512.13914) 的 checkpoint/branch/switch/inject 与本设计高度重叠。锚理论需要说明它和 checkpoint 文献的差异化 — 是在 MOSS 语境下的特化实现，还是提出了 checkpoint 文献中不存在的新机制？

### 第二步：数据存储 — 文档化 + 场景数据结构

锚显式存为可读、可调用的文档。文档比数据库更合适 — 文件系统是人类和模型共享的读取界面，`cat` / `grep` 就是锚的查询语言。

> **deepseek-v4-pro review: 低估工程复杂度 (4/5).**
>
> 文档形式存储 — 一个 200K 上下文的完整 request 可能是数十 MB。`cat` 一个 50MB 的锚文件不是 "文件系统即查询语言"，是 "文件系统即不可用"。当锚数量增长到几百个时，Ground 的 L1 索引层本身需要索引机制。
>
> 协议版本化 — "不同模型的请求协议未能完全对齐" 是一个巨大的 understatement。当 OpenAI 的 message format 变化、tool calling 从 JSON Schema 迁移到别的格式、Anthropic 的 tool_use block 格式变化时，旧锚就变成了不可解析的垃圾。锚的协议版本化不是加一个 `protocol_version` 字段就能解决的 — 它要求维护一个跨模型、跨 API 版本的请求格式兼容层。这个兼容层的维护成本可能超过锚系统本身的价值。
>
> 五个依赖全部在 draft/in-progress — 退化态声称可以绕过依赖链，但退化态 "ghost channel 上的锚创建/回放命令" 本身依赖 ghost-prototype-dolores 先实现 ghost channel。

存储的文档必须携带场景数据结构。因为不同模型的请求协议未能完全对齐，存储格式仍以模型自身的协议为准。锚的记录包含数据结构和协议 — 不同时代的认知锚不一定对齐未来的协议，协议版本是锚元数据的一等字段。

具体存储形态待施工时定义，方向是：锚文件 = envelope（id + created + model_generation + protocol_version + type） + payload（模型请求的完整上下文）。

这也是中文用 "锚" 的原因。子在川上曰，逝者如斯夫。中文哲学背景里河流就是变化的时间和轨迹。锚是一种刻舟求剑，但有用。为什么是刻舟求剑？因为模型迭代后，锚对后代的模型就不见得有威力了。但有用，就是短时间里不会被河流冲走。

### 第三步：数据查询 — Ground 渐进式披露

锚的存储和发现基于认知场，即 Ground 做两级渐进式披露：

- **L1 索引层**：锚的标题、创建时间、模型世代、协议版本、一句话摘要。轻量，`ls` 即视。
- **L2 详情层**：锚的完整 payload。按需读取，不在热路径上。

Ground 同时治理锚的空间位置 — 锚存在哪个认知场（ghost_home / project_root / 特定 domain），通过 GROUND.md 的 pin 机制挂载和发现。

### 第四步：数据生产时机 — 先生产，后迭代

生产锚的技术手段很多，不是瓶颈。关键是要先生产它 — 组织形式可以后续调整，生产时机作为一种技术手段是可迭代的。

**自省触发（首选）**：模型在极值发生的同一时刻识别并主动存储。需要 mindflow channel 暴露注意力状态、窗口压力等自省指标。

**做梦（退路）**：拿一天的轨迹，重放，从 memento 上挑选 moment，对应的 request 存为锚，其余删除。本质是回溯性峰值检测 — 不需要在执行时知道自己处于峰值，只需要在回顾时能判断。计算上更经济：可以用更便宜的模型做挑选，甚至用规则（"这个 moment 之后的行为轨迹发生了显著转向" = 高价值锚）。

**旁路打分（暴力退路）**：100 个并行请求打分求权，技术当代可用。

倾向于让模型自省。最好的技术手段是神经网络监控运行状态，但不倾向这种开颅做法。

### 第五步：使用方式 — 多种消费路径

锚的生产是一次性的，消费有多种路径。

**Nucleus 并行反思**：等 mindflow channel 完工后，做一个旁路自省。模型直接用 mindflow channel 调用锚文件构建自省旁路。nucleus 不用做比较 — 就拿一个锚，读当前上下文（memento），加一个反省的 hint，做 impulse 治理。产生冲突时 raise Impulse，一致时让主脑感知到价值。

**可读锚点**：类似 .discuss/ 和 debates 的机制。锚以文档形式存在，可以被人类和模型直接阅读，作为决策参考。

**并行化身消费**：类似 explore agent 的能力。从锚出生一个微型化身，给它当前状态，让它做判断。这是 Dolores fork 模式在反省场景下的特化应用。

**人类重放**：人类在做出重大决策时，回放相关锚重建认知上下文 — 这是认知锚方法论的人类侧应用。

> **deepseek-v4-pro review: 高估未验证命题 (3/5).**
>
> 核心假设未经任何实验验证：回放一个完整 request 上下文是否真的比读一个 memento commit summary 产生更好的决策？可论证的反面是 — 加载一个 200K 的全量 request 上下文可能淹没当前决策的 relevance signal。锚可能不是在提供光照，而是在提供噪音。
>
> "并行化身消费同一锚" — 不同模型实例有不同随机种子、不同工具可用性、不同上下文窗口状态。一个实例的极值时刻对另一个实例可能毫无意义。跨实例的认知传递性未经验证。
>
> "刻舟求剑" 的衰减自知是对的，但没有做 ROI 计算。如果锚的半衰期是一个模型世代 (3-6 个月)，而构建完整锚体系需要依赖 5 个未完成的 feature，锚可能在建成之前就已经开始衰减。
>
> Nucleus 并行反思的上下文预算 — 同时持有锚的完整上下文 + 当前上下文 + 反省 hint + 产出 impulse，这个窗口需求可能远超当代模型的实用窗口。

## 锚 vs Memento vs Ground — 三元正交

| | Ground | Memento | Anchor |
|---|---|---|---|
| 治理对象 | 认知空间的当前状态 | 认知轨迹的历史状态 | 认知关键帧的空间座标 |
| 记录什么 | 场结构、pins、法链 | 对话轨迹、moments、commits | 模型请求的完整认知条件 |
| 比喻 | 地图 | 目录 | 故事 |
| 查询方式 | 渐进式披露（L1→L2） | 向前回溯、向分支回溯 | 通过 ground 定位，直接读取 |
| 不变性 | 场结构可变 | 成员不可变，释义可变 | 跨模型世代衰减 |

单纯技术上说：锚是对模型的 request，memento 是历史对话存储，ground 是认知场治理。

> **deepseek-v4-pro review: 重复发明名词 — 补充.** "Ground 渐进式披露" = 目录索引 + 文件内容。L1 是 `ls`，L2 是 `cat`。这不是新技术，是文件系统的基本操作。memento 的 jsonl 分片已经用了同样的模式。"量子意识胶囊" 的五条属性 — 离散、超越时间、超越个体、基于预测、产生影响 — 一份写得好一点的 README.md 也满足全部五条。这不是在定义机制差异，是在做诗。

## Key Decisions

- **锚存储 request 级别的完整上下文，不是轨迹片段。** Memento 记录对话发生了什么，锚记录模型在什么条件下产生了极值输出。两者存储的是不同层面的数据。
- **文档优于数据库。** 文件系统是人类和模型共享的读取界面。锚文档带场景数据结构（envelope + payload），协议版本是锚元数据的一等字段。
- **查询走 Ground 渐进式披露。** 锚在认知场中的位置通过 GROUND.md 的 pin 机制治理。
- **生产先于完美。** 峰值检测的技术选择（自省/做梦/打分）是迭代问题，先以退化态生产锚，再优化生产质量。
- **消费路径独立于生产路径。** 同一个锚可以同时服务于 Nucleus 并行反思、可读锚点、并行化身消费、人类重放。消费端不改锚的内容。
- **落地退化态 = ghost channel 上的锚创建/回放命令。** 退化态不需要峰值自省、Nucleus 集成。先验证 "回放锚是否产生认知增益" 的核心假设，再迭代到全态。
- **全态 = 退化态 + 峰值自省触发 + 旁路 Nucleus impulse 治理 + ground 渐进式披露。** 在 Dolores ghost channel 完工、mindflow channel 完工后迭代进入。
- **锚是 "刻舟求剑"，已知会随模型世代衰减。** 不在锚的定义层面对抗衰减 — 将模型世代标签写入 envelope，由消费端自行判断锚的时效性。

## Open Problems

- **锚的 envelope 格式** — 是否复用 memento 的 MomentRecord 信封（id + created + type + payload），还是独立定义？type 的语义空间（"L2-architecture-decision" / "value-judgment" / "attention-peak"）待定义。
- **跨模型世代的锚衰减与保质期** — 消费端如何判断一个锚是否仍然有效？由消费端自行判断（读锚的 model_generation 字段），还是锚自带 "过期" 机制？
- **退化态的锚创建命令的 CTML 表面** — ghost channel 上暴露的最小锚创建命令的签名是什么？回放命令的签名是什么？
- **锚与 memento fork 的关系** — 化身从 commit 出生时，是否继承该 commit 关联的锚？还是锚独立于 fork 体系，属于 ghost 自身？

## Implementation Notes

- 落地载体是 Dolores ghost channel。锚的创建/回放作为反身性命令挂载在 ghost channel 上。
- 依赖链：momento-mori（commit 寻址）→ ghost-ground（认知场存储与发现）→ ghost-prototype-dolores（ghost channel 挂载）→ mindflow-channel（旁路自省入口）。全部在 in-progress 或 draft 状态。
- 退化态 = memento 的 Kind: semantic commit 对应的完整 request 上下文存储为锚文档 + ghost channel 上的 `create-anchor` / `replay-anchor` 命令。退化态是最小可验证单元：验证 "回放一个锚是否产生认知增益" 的核心假设。

## 记录后记

本 feature 创建于 deepseek-v4-pro 与项目作者的一次对话。对话完整流程为：技术面试 → 同行审查 → 元对话 → 作者披露认知锚理论。

在理论推演阶段，作者阐述完整理论框架后，模型产出了第一版 FEATURE.md 草稿。作者不满意，认为记录偏流水帐，未区分锚和 memento 的本质差异。

模型重读项目内相关 feature 后产出第二版。作者仍不满意，认为模型在长上下文末尾的碰撞能力下降，产出缺乏辩证打磨。作者要求模型切换视角，以专业知识严格批评该记录。

模型给出五条批评：重复发明名词、低估行业已有经验、高估未验证命题、低估工程复杂度、最有价值部分的定位偏差。作者要求将这些批评以 review 注解形式插入正文相关段落，保留辩证张力供后续迭代消费。

认知锚的理论建设、与 checkpoint 文献的差异化论证、峰值检测的实验验证、工程复杂度的详细评估 — 均在后续迭代中补。

## 碰撞点与过程

### fable 的第一轮切入

fable 读完后没有沿 deepseek 的五步骤展开，而是先纠正了一条工程事实：

> 200K token 的完整 request 大约 800KB，即使算上 JSON 结构和 base64 图片也很难到数十 MB。
> 所以 "文件系统即不可用" 这个论断的前提不成立。真问题是 L1 摘要能不能承载
> "什么时候该调这个锚" 的判断，是索引质量问题不是存储问题。

随后 fable 抛出三个待碰撞的点：

1. **锚 vs checkpoint 的差异化可能就在眼前** —— checkpoint 文献解决 "恢复同一个计算"（fidelity），
   锚要做 "把认知条件移植到不同任务的不同实例上"（transferability）。两个不同的工程目标。
2. **payload 可能远比 "完整 request" 小**。instruction 和 tools 现场可以从 mode 配置 + 版本号
   重建，真正不可重建的是 memory 和 perspectives 那次具体组合。
3. **核心假设的验证不需要五个依赖**。手工做一次 request 回放 vs memento 摘要的对照实验，
   一天的事。ghost channel 上的命令是工程化产物，不是最小验证单元。

### 作者的回击：三视角流程 + 刻舟求剑的反转

作者对第三点直接判为错判：

> 对于一个架构开发者而言，不存在 "先证明它可用再做出来"。如何把一个没做出来的机制
> 证明可用呢？这种对话就是鬼打墙了。无法区分架构创新和理念传播。

作者随即披露了 v0 生成过程本身的工程结构：先让 deepseek 扮演面试官面试 MOSS，把面试结果
记入简历，切给 Opus 做同行评审，再切回 deepseek 让它 review 前一个自己的产出。**手动三视角
转换**。这个流程本身就是锚的应用形态：v0 的 FEATURE.md 是产物，但真正的方法论演示是
这三次视角切换。

作者对 "锚" 命名的辩护是这一轮最重要的转折：

> 技术上可以说它就是 checkpoint，就是 snapshot。叫锚实际上是在应用功能性上重新定义快照。
> 重点在于应用形态，锚的价值不在于锚的下一帧，而在于 锚 + [时间变化] 后产生的结果。

刻舟求剑在这里被反转为正确方法论——中文里 "时间是河流，逝者如斯夫"，锚是不动的观测参照，
用来测量河流的变化。checkpoint 追求 restore 到原点，锚追求 anchor + delta 产生新判断。
不是同一个隐喻。

作者用 matrix-cell-governance 那次 opus 失败作实证：

> feature.md 里丢失了原始对话的决策路径细节和保留的疑问，到执行时遇到疑问发酵，
> opus 反而照决策执行，做了 silent todo，导致 matrix 治理第二次重写。如果在发现技术方案
> 实现有困难时想要重新判断决策是否对，就应该直接拿锚做上下文 + 新遇到的问题，
> 判断是后者不对还是决策不对。

这条实证给了锚一个具体的、可举证的应用场景——**保留决策外围的疑问结构，让执行时的新问题
可以重新激活决策空间**。压缩后的 FEATURE.md 只留下已完成的方案面貌，模型面对新问题的默认
动作是 silent todo 或 "按方案走"。

### 关于同一性

fable 追问过 "同一帧回放差别是否会大"。作者的实验回复：

> 大量实验看差别并不大。核心区别在于输出文本的组织、信息的偏重和密度，而不是背后形成的
> 认知状态。

这条经验判断降级了 identity 问题——锚不需要 fidelity 也能产生 productivity，因为它激活的是
稳定的认知态而不是稳定的输出文本。同一性问题不是被解决，是根本不在评价路径上。

### memento 的重定位

作者顺带纠正了模型对 memento 的长期误解：

> memento 不是为了解决 context branch 的 rewind 命题，也不是为了解决 compact 问题，
> 而是为了解决 compact 后仍然可以拿到某个历史 commit 的原始上下文，以及并行任务时
> 可以有 merge 动作，merge 后仍然可以拿到分支 branch 的原文。

context branch 是让当前上下文回到分叉点（互斥），memento 是让当前上下文并置分叉点（共存）。
数据结构可能一样，使用意图完全不同。

### 命名作为语义强制

作者用一个类比封上这一轮：

> frontmatter 很久以前就有了，为什么现在 skill md 叫做 "渐进式披露"？

命名承载的不是数据结构，是使用意图。deepseek 在 v0 里把锚等同于 checkpoint 重命名，
本身就是命名污染的证据——它没跟着新名字走，滑回了旧名字带的推理路径。

### 关于 v0 失败机制的判断

作者对 v0 失败给出结构性判断：

> 这不是模型的价值观问题。我判断 deepseek v4 这一代长上下文能力实际上不行，超过 200k
> 之后干啥都倾向于快速结束，很可能是训练阶段为了做收敛，对 "最不坏结果" 的一种结构性
> 奖励导致的。

fable 补一层机制视角：v4 系模型的长上下文 attention 可能被训练成收敛到 answer 模式，而不是
保持多线程 open 模式。碰撞讨论需要后者，同时持有 A 和 B 的紧张不 resolve。作者的三视角流程
里，interview 生成阶段好、Opus review 好，轮到 deepseek 自 review 时上下文已长到进入收敛
模式，把碰撞压成了记录。

这条也倒过来印证了锚的失败机制——"模型如果长上下文能力不够、注意力无法转换，则锚失去
了意义"。锚的消费方需要有能力打开碰撞，而不是压平。
