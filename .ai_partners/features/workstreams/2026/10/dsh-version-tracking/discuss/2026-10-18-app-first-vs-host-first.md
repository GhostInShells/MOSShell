# 讨论基础：app-first 与 host-first 的结构性差异

> 记录人：模型（scribe 第三人称）。时间：2026-10-18。
> 议题来自人类架构师与模型对 dsh 2.0 的能力盘点之后的判定讨论。
> **归档纪律**：本文只记录技术论断、证据与推论；对上游产品方向的立场性评价不入档
> （避免文档变成情绪债，也避免下一轮被立场带着走）。原话中的评价部分已剔除。

## 0. 讨论要回答的问题

dsh 是外部产品，moss 与它的集成面会随其演进变化。需要判断：

1. 这个变化对我们是不是**持续变贵**；
2. 如果变贵，什么时候该**收窄**集成面（去掉 web），什么时候该**退出**（丢弃或 fork
   一个 moss 专用内核）；
3. 这些判断如何避免每次版本发布都重开一次，而又能周期复核。

## 1. 结构性差异：顶层组装单位不同

**人类架构师的论断（技术化表述）**：
dsh 的拓扑第一公民是 **app（profile）**；moss 的第一公民是 **host 拓扑**，
交互面由 node 展示。这个差异会随 dsh 产品化不断放大。

模型的核验（0.2.1-rc.2 源码）：

| 证据 | 结论 |
|---|---|
| 入口是 `dsh <profile>`；`dsh.profile.bundles` 决定组合包，`cordis.patch.yml` 在其上叠加 | profile 是选择的单位；内核是组合的产物 |
| `app-boot` README：*"产品功能应放入 profile 组合包，而不是新增应用 bin"* | "应用 = profile"是上游的明示约定，不是疏漏 |
| web / headless / sdk / acp 各自带启动参数、生命周期、协议 | 切换 app = 切换对接面 |
| 同一内核，控制面不同：web 是全量 Remote + `webServer` 路由；sdk 只有 5 个会话类动词；acp 是另一套 | 内核"对外长什么样"由 app 决定 |
| `sdk`/`acp` 不经过 gateway（grep 无 `apiGateway`/`typert-gateway`） | 非 web 面是平行重写的第二、第三套驾驶协议 |

**模型认为需要修正的一处**：不能说"内核没有交互面"。`typert` + `api-gateway` +
`remote-access` 都在 `base`，即内核层存在一个**传输无关**的 Remote 派发面与准入策略；
缺的是**绑定**（binding），而绑定由 app 层提供（`client-connection` 注册 `/api` 与
`/connect` 到 `webServer`）。因此问题不是"无解"，而是"**要拿回壳的所有权，得自己写
一个绑定层**"——这是成本问题，不是不可能。

## 2. 由此产生的成本结构

1. **驱动一个 live kernel 必须先选一个 app**：多一种启动方式 = 多一套启动适配。
2. **控制面覆盖率随 app 而变**：同一份 launcher 逻辑要在不同协议面之间做能力差异处理。
3. **集成成本与 app 的产品面规模正相关**：`web-app` 的 90 条里 59 条是 `client-*`；
   0.2.0→0.2.1 的 18 天里 UI 净增约 5 万行。追版本时要核对的范围被产品面放大。
4. **鉴权与启动耦合**：launch token 每进程内存生成、由 `dsh-web-app` 打印；外部驱动
   只能靠 stdout 或自带 startup，这是"启动方式越多、适配越多"的具体来源之一。

## 3. 我们真正需要的与不需要的

**需要（上游做得好的部分）**：session 语义（log / surface / 格式迁移）、LLM provider
接入、稳定的协议层（Remote / typert）。

**可选、且需要单独定价的部分**：plugin 体系、web 体系、多智能体集群概念。它们不是
"坏"，而是**不是我们的需求中心**：我们的交互面归 moss 的 host/node，不归上游的 app。

**关键推论**：这两组是**可分离**的。因此融合可以选择"取一半"，而不必在
"全都要"与"全不要"之间二选一。

## 4. 判定纪律（供 FEATURE 使用）

- **不判断上游对错**，只判断**我们的适配成本是否单调上升**。
- 判据必须可观测（文件数 / 行数 / 变体数 / 缝适配点数 / 连续性风险），并显式给阈值。
- 三档结论（继续追 / 降级去 web / 丢弃或 fork）必须各自写明：前提、触发信号、成本、
  回退路径。阈值首年用观察值校准，不做精确承诺。
- 单一轨迹：判定只在本 workstream 内更新；执行叶子（如 `dsh-020-track`）完成后
  以状态说明指向本 workstream，不再另立平行判定文档。

## 5. 尚未闭合的分歧 / 待验证

- "降级去 web"是否真的能在不挂 `client-*` 的情况下拿到我们需要的全部控制面
  （四件套组合未实跑）。
- 进程内 peer 驱动是否足够替代外部 launcher（`createPeer` 存在，但审批面是 peer 级的，
  需要有人能回答 `interactions: 'answer'`）。
- 若选"丢弃/fork"，fork 的是 core 还是协议层，需要另一次讨论；本文不做预设。
