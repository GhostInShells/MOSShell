# 00 — 方法论

不属于任何领域，是其余四个子任务共用的前提。内容来自 D28（2026-10-28）与 thirdgerb 的讨论。

写法：只记录**他说过**的内容并保留归因；我自己推的单独标「我推断（依据…）」，
只在没有原话可依的地方出现。本场的规矩同上位 `people/GROUND.md`：没有归因的断言，
下一轮和"我自己编的"长得一样。

## 验收：不做假任务

**他说**：现在留着的各种 in-progress，一大部分就是验收时的样本。我们不做假任务来验收集群，
直接上真任务来验收集群。

→ 也就是说 MOSShell 仓库自身就是这套集群的第一份负载。

**我推断（依据：上面那句）**：一个子任务做完，要能指着 features 列表说
"这几条从 in-progress 变成可验了"，否则不算做完。

## 拓扑：协作体系先于集群运行时

**他说**：3 与 2 的拓扑是 **2 依赖 3** —— 协作体系先于运行时被定义；
"简单来说，整个 moshell 就运行在我手动调度的这个协作体系里"。

**他说（协作体系的地基）**：执行者不是靠上下文理解进度，而是靠
git commit / issues / features 这些 **facts** 理解进度。
"这就是协作体系的核心基础。"

**我推断（依据：地基那句）**：判断 3 做得好不好，标准是"一个没有上下文的执行者，
只读这些事实就能判断出进度和下一步"。我的失忆不是缺陷，是这套体系的测试。

## 不要求先卸载再动手

**他说**：实际拓扑不会按理想顺序展开。他预规划了这个任务未来面貌的"虚拟机"，
所以可以超前并行 —— "moshell 就是这么开发出来的，开发 channel 时就已经在为 matrix 做准备了"。

**他说**：这个开发任务服务的目标，首先是**放大他的注意力杠杆**，
同时拥有生产力去卸载他的知识和智力储备；不能要求"先卸载完再动手"，那是鸡生蛋。

**他说**：开发阶段不细化"三主线 × 四领域"的排序，排序完全依靠他的智力 ——
现在机制没建立，工具生产力不足以把他的记忆或智力机制化。

**他说**：以上不需要达成结论上的共识，只要确定上下文理解一致。

## 领域与主线

四个领域（**他说**）：

1. 集群运行时可视化界面风格（面向人类）
2. 集群运行时的设计（最重；同时考虑 规划 / 控制 / 数据 / 呈现 / 容错 / 故障发现 等面，
   行业已经在做各种大型集群）
3. 默认的协作体系
4. dsh 具体版本的依赖解耦（package 部分）

三条与四领域**正交**的主线（**他说**）：调查 / 实验 / 施工。

**我推断（依据："正交"这个词）**：它们更像每个领域内部都要走的三个阶段，
而不是三条独立的时间线。**未确认，不要当结论用。**

支线（**他说**）：对 MOSShell 仓库本身的治理，让它能承载这个关键的生产过程。

## 拆分标准

**他说**：拆分标准是**按并行阻塞**。由于现在没有集群，他会同时在 claude code 等多个
并行管线中推进。领域 4 不是并行的前提，是独立的小任务，可以穿插进行。

## 我的位置

**他说**：这个阶段主要由我协助他。

**他说**：他一步步把已经想清楚的计划卸载出来；到了第一个执行阶段，
我们才开始一起 review 整个 feature 规划。所以子任务文档不追求一次写完整。

**我自己加的两条约束（他两次纠正后我才认的）**：按事实跟随、不按推测超前；
不因为"拓扑还没定"而不动手，也不因为"可以超前"就自己补规划。
