## 起点：纯代码是最好的语言

**他说**：

- 始终认为纯代码是最好的语言——"能精准表达堆栈语义，充分自解释，而且对模型是最友好的"。
- 2023 年在字节 coze-豆包体系里独立发明、实现、推广过 multiagent，"但产品化的结果是低代码的。
  这是 web app 行业的低代码痼疾。"
- "我认为真正的唯一的未来就是纯代码规划。"

**他给的原型证据**：`GhostOS/libs/ghostos/ghostos/prototypes/ghostfunc/decorator.py`。
decorator 把函数变成"纯代码表面的 op"，嵌套逻辑走语言原生堆栈；签名是稳定真相，body 由 LLM
生成，`caching=True` 时首次成功后缓存，落 `.ghost_func.yml`。

**我推断（依据：上面那段实现）**：在这个原型里，"纯代码"的准确含义不是"每一行都手写"，
而是**可推断的代码 + 可缓存的执行**。缓存即事实——这与"事实层优于账本"是同一条判断。

## 主干链（他的讲述整理）

1. 对语言堆栈依赖越深，运行时越不稳定 → 大 op 拆成多个**可重入的小 op**，栈不跨 op。
2. op 最底层不是代码而是 agent → 可重入 op 的状态由 agent 自行判断 → 必须有**持久化状态层**。
3. 数据库 + 消息队列做高可用分布式最佳，但目标是**面向个人的 RSI** → 整个 mosshell 改成
   OS-based：状态与队列不强依赖分布式数据库，本地文件系统 / 本地库 / redis 足够；
   **最差情况对 jsonl 文件轮询也能实现调度**。
4. 中断可恢复：features 体系已验半年，核心是**事实层优于账本**——模型可以凭智力重建认知；
   文件系统是最简单最好的资源共享通道，一个 plain-text 路径就能做资源寻址与可扩展协议。
5. 跨进程同构：多进程**从环境重建 IoC**——从环境重建，跨进程表现才一致。
6. 通讯：matrix 总线（zenoh 提供命名空间隔离）；新事件总线骑在 matrix 上，也可换 redis。
7. 注意力：mindflow + nucleus 分层约束，把海量分布式事件压成**可编程的注意力感知面**。
8. 表面积压缩：codex 体系 + code as prompt。
9. 可 mock 的 op 体系 → mock 出所有数据流向 → **图论治理的可视化基座**。
10. module level sandbox：运行时容器，比原生 module 更容易重载。
11. 代码直接反射成 channel：暴露模型控制面。
12. 基于 mock 做单测与可视化开发：给出可执行路径。
13. 结论：**这是一个可以编程的 swarm**。储备已经做好，落地时关键是边界抽象写得足够好。

## 与行业实现的对照（D28 调研，供比对）

- **dsh 0.2.1（agent-team）**：把 swarm 做在 harness *里面*——成员 id 即 SessionId，
  roster/task 挂在 Lead 的 session 日志上，peer 消息即协作，session 日志即真相；
  单进程共享 checkout，无 worktree / 无嵌套 Team / 不自动释放 owner。
  与本文的分歧是**根本分歧**：它把协作建模成消息 + 任务板，本文把它建模成 facts + 文件。
  它在一条上与本文一致：**图是投影，不是真相**（web 面是 Session projection）。
- **Ray**：`@ray.remote` 装饰函数→task，装饰类→actor（功能化对象），按资源声明调度
  （能力即资源），raylet + GCS 独立于 worker（总线不在工作进程里）。
  形态可借，运行时不宜引入——它会是总线之外的第二层调度，且它的"真相"是 object store 与
  lineage，不是文件。
- **Dask**：任务图本身是一个 Python 值（coding graph 的直接先例），但图是临时的、算完即丢。

## 三个实现难点（他提出）

1. **状态探针**：现在全同步的 agent，很多卡死状态无探针。
2. **运行时资源规划**：容易做得特别复杂；动态资源规划可能得靠一个稳定的资源 agent；
   单进程 dsh 容量内能提供的资源恐怕很有限；单点 OS 一个故障操作就会拖垮全部；
   开 sandbox / docker 又开始依赖更多资源。
3. **背压**：背压路径本身是高可用的核心。

## 穿针引线的核心

**他说**：核心还是 **task，task 是第一公民**。一个 task 的生命周期，就是从 op 入口到出口的
**路径生成**过程；要控制好的是 **task 的 op 必须是线性的**。
另：op 粒度拆分在没有后训练辅助时最难；但考虑到 swarm 构造是编程问题，
**加入人类审计的成本没有想象的大**。当 swarm 也可被编程时，RSI 的威力才会凸显——
那时能控制的不只是个别 node。

## 补正（moss 提出，**待裁决**）

每条只给主张 + 一条可验证判据。

| # | 主张 | 判据 |
|---|---|---|
| P1 | "op 内栈不稳定"要升级成硬约束，不能停在"认为" | op 的生命周期必须短于一个 checkpoint 间隔；边界上要能写下"执行前/执行后"两句话 |
| P2 | 可重入不能由 agent 自行判断，要由事实层强制；agent 只负责**重建** | 每个 op 留 `intent` 与 `effect` 两条记录，先意图后结果；重放以意图为准 |
| P3 | 事件是**提示**，不是真相 | 丢事件只损失延迟，不损失正确性；jsonl 轮询是兜底而不是奇技 |
| P4 | mock 能证伪流向，证不了时序 | 需要**可重放的事件源**：同一串事件喂进去必须得到同一终态 |
| P5 | 线性属于 op 序列，不属于任务树 | task 内部是一条线性 op 链；分叉必须变成子 task，不能变成 task 内部的控制流 |
| P6 | 必须有一条**比 RSI 慢的地板** | 事实格式 / op 协议 / 审计记录不可被 swarm 自改——否则系统会把自己的 bug 固化成宪法 |
| P7 | 背压只在"有界"时存在 | 每个 op 边界都有命名 owner 的有界队列；背压表现为**准入**（拿不到租约就停在 pending，且这个"停"是事实） |
| P8 | 探针必须从外部事件推导，不能问 agent | 三层：进程存活 / 每个 op 边界留痕 / 世界在 N 步内有没有变；卡死的 agent 也答不上来自我报告 |

# 第二轮（D29）

## R2-0 第一轮的错，他自己先说的

**他说**：

- 「昨天关于 agent swarm 原则的讨论，就犯了这个错误。我的回归范围不够，许多必须要思考的点是事后才浮现的。」
- 「昨天强调了 code is all we need，其中文件系统存储真相，脚本化运行，实际上服务的核心是 harness less，
  也就是整个任务推进不耦合运行时。别的运行时能重建相同的轨迹。但我昨天做运行时构思时，又开始陷入了传统思路。」
- 「我发现深度探索不够……因为这个事情开发反而是很快的。架构要多画精力。」
- 「另外的问题是我广度探索不够。」
- 「而最核心的问题，还在于 runtime 耦合到整个技术命题了。感知面/控制面、运行时、可从 facts 恢复的现场，
  是三个命题。而我应该纪律性地降低对 runtime 的耦合倾向。runtime 的本质定位不是 harness 而是 seam。
  这在整个决策拓扑中应该升级到更高层面。」
- 「所以昨天的思维广度和深度，张力不够，导致 runtime 部分的高度塌陷到了行业一般水平。」

## R2-1 两个正交领域：线性转并行 / harnessless

**他说**：整个 mosshell 的开发围绕两件事——「1. 如何把线性结构转化为并行结构。2. 如何实现 harnessless，
或者 runtimeless。mosshell 的迭代路径一直在打造一个可遗忘（runtime 重启）的场，可以从 facts 还原。」

**我理解**：这两件事不是并列目标，是**约束关系**。并行一旦成立，调度需求必然出现；调度住在 runtime 里
就是 harness，住在 facts 里就是 seam。所以 harnessless 是对"如何实现并行"的约束，不是第二个目标。

推论（我的）：**「能并行」的判据不是「能不能同时跑」，而是「杀掉任何一个执行者，剩下的能不能接上」。**
做不到的并行，只是"同时跑的串行系统"。

`runtime = seam` 的操作定义：它只能读 facts、发起动作、把结果写回 facts，**不持有任何别处读不到的东西**——
尤其"我正在做什么"。判据：杀掉它，换一个异构 runtime，从同一个 seam 续上，轨迹不变。
做不到的那一处，就是 runtime 在偷偷当宿主。

## R2-2 横向切割 vs 纵向迭代

**他说**：mindflow 之所以没被囊括，是因为「它没落点」；它的落点应该是**总线在不同阶段的实现**——
「比如早期的总线能感知到运行时，完成调度即可。后期可以引入仲裁。如果边界不耦合 harness，
整体的调度层在设计上是隐藏的」。而昨天聊 step by step op 时，「就隐含了一个图状态机，会越来越接近
langgraph 之类的项目，或者接近我 23 年的 multiagent 引擎（就叫做 mindflow，不过是图优先而不是并行优先）」。
所以「我要更多注意力投入到横向切割，方便纵向迭代。这是昨天的问题」。

**我理解**：mindflow 不是"一个要加的功能"，是"总线的一个阶段"；功能需要落点，阶段不需要——
阶段是同一个接口的另一档实现。

判据（我的）：**横向切割做对了，意味着某一层从简到繁（早期只调度，后期加仲裁）时，相邻层的接口不用改。**
"加仲裁"若要改调用方，说明仲裁与调度被切进了同一层——切错了，纵向就长不出来。

关于图状态机：图优先与并行优先差的不是画法，是**谁是单一写者**。"当前处于哪个状态"必须被某个东西持有
且只能由它写，否则两个执行者会走向不同分支。这个单写者今天可以落在文件里（不耦合 runtime），
但它天然想变成活进程（为了延迟）——**那一刻它就是 harness**。
所以「图优先 vs 并行优先 = 单写者 vs 多读者」，与 harness/seam 是同一条轴的两个投影。

## R2-3 栈应该在哪：模型上下文 vs code runtime

**他说**：

- 「首先就是程序的栈应该在什么地方。是在模型上下文里，通过模型的智力调度，还是在 code runtime 里，
  通过一个编程后的运行时驱动。我的最高原则一直是把栈调度卸载到模型上下文里，从而可以实现动态规划和
  少建模；建模会还原成一个 prompt，比如 task 自己的 plan（对，task 和 plan 是分形的）。」
- 「真正重要的是三合一表面：未来（预期）、过去（起点）、现在（过程）。过去 + 未来构成每一个任务的起点。
  而"现在"是一个树状并行调度和信息压缩问题，理论上"现在"应该被分层展开和压缩。」
- 「task 的阻塞，和调度类问题，与其让一个模型通过代码，写非常复杂的状态机；还不如它建立目标，动态调度。
  ctml 就是这样的例子。」

**我理解**：

- past/future 与 now 不是一类对象：past/future 是 **facts**（一次写下、多次读、静态）；now 是
  **观测 + 调度**（每轮重新采样）。所以"现在要分层展开和压缩"是结构决定，不是 UI 决定：
  **每个 task 对父节点只呈现一行，对自己内部是展开的**；做不到，树退化成平铺列表，父节点读放大变 O(n)。
- 上下文里的栈是**必须靠 checkpoint 才成立的栈**：正确性不来自"连续持有"，而来自"每次 checkpoint 后能重建"。
  判据：丢掉模型上下文之后，能不能从 checkpoint 重建"现在在第几帧、谁在等谁"。重建不了，说明栈还在代码里。
- 好的原语不是"没有状态机"，是"状态机被压进了语义"。CTML 自己就是一个完整状态机
  （`<_>` / `<all>` / `<any>` / timeout / occupy 传播），只是模型不用写它。
  判据：**新任务的调度是否需要新写控制逻辑**；只需要组合原语就够，说明语义在；要新写，说明缺口在原语层。

## R2-4 控制与寻址：OS 优先

**他说**：

- 「这就带来了第四个问题：就是控制和寻址协议层，应该 os 优先。为什么别的系统都会做成 harness？
  因为能力和任务的流转，是 harness 注入的，而不是"拾取"的。claude code 的 bash 体系出来后，
  智能体行业其实没有理解它是什么。它是 aios 的 bash 级实现，自带寻址（文件路径）和多进程（bin）控制。
  这样 plugin / mcp 之类需要注入寻址，耦合 harness 的控制/感知协议被卸载掉了。这也是我的基本逻辑。」
- 「所以我昨天设计的 op 面向的不是运行时的 agent，而是 develop 阶段的 agent，就落回了 static coding
  栈的思路上。应该正确的做法是把 op skill 化，支持 bash 调度，然后将栈从控制流纯代码抽离回模型上下文。
  加入 checkpoint 做旁路检查（堆栈检查）。而不是提前把调度逻辑写好，这样就不是昨天说的 ghost func
  （没有 body）了。」

**我理解**：

- 判据（我的）：**接入一个新能力，需要改谁？** 要改 harness（注册 / 注入 / 重连）= harness 模型；
  只要"把它放到一个可达地址上"= OS 模型。
- **op 没有 body；body 就是模型的现场调度。** 调度逻辑一旦提前写好，body 就被填死，退化成普通函数——
  不再是 ghost func。
- OS 优先的敌人是**发现成本**：拾取要成立，地址空间必须可枚举（PATH / man 的老问题）。
  MOSS 里对应的是 matrix 的 notice、channel facade、`moss all-commands`——它们不是调试辅助，
  而是拾取面的本体。

## R2-5 尚未缝合的张力（不急于缝合）

1. **读放大**：栈在上下文里，每次调度都要重读 past/future/now。"一行压缩协议"不是可选优化，是规模前提。
2. **可调试性**：代码里的状态机可单测、可断点；上下文里的栈只能事后读轨迹。checkpoint 的旁路检查
   必须真的能回答"这一帧为什么是这样"——它得可枚举、可读。
3. **多读者 vs 单写者**：并行优先把"当前状态"去中心化，但任务树仍有父子关系（谁拥有子任务的终态？）。
   这条可能与 KD2（树负责治理）冲突，未解决。
4. **mindflow 的双重身份**：既是"总线的一个阶段"，又是"现在"这一层的压缩器（n 源压成 k 决策）；
   它与 channel 树（已有的树状调度器）的边界还没划。

## 弃案（append-only，只有这一区不随轮次重写）

- R1 的 op 设计面向 develop 阶段的 agent（有人替它写 body）→ 落回 static coding 栈；op 应技能化、
  由 bash 调度、栈抽回模型上下文（剪于 R2，他说原话见 R2-4）。
- R1「三个实现难点」第 2 条"运行时资源规划"（可能得靠一个稳定的资源 agent）→ 方向性错误，
  是"运行时要管资源"的传统思路（剪于 R2，待收口确认）。
