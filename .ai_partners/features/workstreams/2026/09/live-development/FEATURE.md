# Live Development — 开发过程本身作为可观测的产品

> Use `moss features set-status live-development <status> -m "note"` to update state.
> See [TOPOLOGY.md](TOPOLOGY.md) for directory layout and [README.md](README.md) for the full convention.

## Motivation

**这是一条 user story, 不是一组功能。** 其它 feature 服务于它, 它自己不服务于任何一个
功能目标。

原始出处是项目最早的用户故事 (2026-05-18, 早于一切实现):

> 我在开发这个项目时, 桌面摆着一个桌面机器人。它能身形并茂地和我对话, 同时能协助我开发,
> 能管理音乐播放, 能看到我主动打招呼, **能直接回应我直播时直播间的弹幕并协作**, 能随时帮我
> 记录信息, 能陪我一起看视频, 读文档, 帮我记录信息。我不在的时候, 能帮我向别人介绍这个项目。
>
> — `.ai_partners/features/workstreams/2026/05/ai-docs-topology/discuss/2026-05-18-architecture-topology-alignment.md:17`

`vision-first-class` KD10 已经先落了一小块, 并把原则写明了: MJPEG 流的定位是
**"人类的直播开发流 —— 让人实时看到 ghost 看到的画面 (直播、开发调试)"**, 且
**"人类直播是最苛刻的合法消费者, 采集帧率由它决定"**。

**为什么现在**: 依赖首次接近齐备 (语音 / 屏幕 / 编辑面 / 形象 / 视野 / 推理核), 而且
阶段三需要一条能把它们全部压测一遍的 user story。

**为什么它不是 gate**: 它的验收是一次**事件** (一场真的直播开发跑通了), 而 stage 的
验收若挂在它身上, 就等于挂在 8 个依赖上。STAGE.md 自己写着这条纪律 —— "do not block
the parallel set on one gap"。它进 stage 3 的 Associated Workstreams, 算**演示目标之一**。

## 核心目的与判据

### 目的 — 人机结对编程

这个机制的核心目的是: **把"人机结对编程"的过程设计出来。**

**为什么必须是结对**: 模型写代码的过程, **同时在给人脑编程一个虚拟机**。这个虚拟机不被
建起来, 模型能做的就只有**可丢弃的内容** (比如 skill —— 丢了重生成就行)。而**架构类内容
不可丢弃**: 它必须被人理解、被人维护、被人接着改。

所以对架构类工作, **沟通的意义本身就很大** —— 它是**认知的双向编程** (模型在人脑里建
虚拟机, 人在模型上下文里建意图), **代码是副产品**。

**因此观测面必须建起来**, 两个方向都不能缺:
- 不让人类不知道模型在干什么;
- 也不让模型不和人类沟通。

**第三方观测视野 = 强迫验收机制。** 有人在看, 就没办法糊过去。

### 判据 — 私有 → 共享

**主题交互内容必须从"私有"改成"共享"。**

今天的人机交互 (打字、终端、模型上下文) 本质是**私有**的 —— 只有在场两人能看见。目标
状态下, **语音、模型操作、讨论** 这三类主内容默认**可被第三方看到**。

这条说的是**内容形态**, 不是"有没有人在看"。观众存不存在不改变它 —— **因为观测面的功能
是强迫, 不是娱乐** (见上)。

## 多视角 (机制的核心, 勿丢)

直播开发的多方观测关系:

| # | 视角 | 观测 |
|---|---|---|
| 1 | 录制视频的观众 | 2 / 3 / 4 |
| 2 | 直播时的观看者 | 3 / 4 |
| 3 | 开发者 (人类架构师) | 2 / 4 |
| 4 | 模型 (含各种 signal 体系) | 2 / 3 |
| 5 | 开发成果 + 过程本身, 作为产品 | — |

2/3/4 两两互观 (一个三角形), 1 是它的**录制合成** (所以 1 ≠ "把直播流存下来", 它包含
2 的观众反应)。5 不是视角, 是**产物**。

判据上的推论: **入向通路是把"录播"变成"直播"的那个东西**。教学/演讲里观众不许插话;
这里 2→3/4 的观测是成立的 (4 关注 2 就是弹幕进感知)。

## 三个可观测要求 (人类 2026-09-18 确立)

1. **直播间信息进入交互感知体系** —— 一个直播间 node 发 signal。**不直播时不需要**。
2. **开发内容本身可观测** ⇒ 主题交互内容都应共享, 具体表现:
   1. 人与模型**不靠打字交互**, 或主要不靠打字 —— 语音是可观测的核心主体。依赖流畅的
      音频自由对话体系, **至少依赖一个基础状态机**。
   2. **模型的操作对人类视觉可见** —— screen (承载多界面)、文件编辑-阅读可视化、bash 可视化。
   3. **讨论/交流阶段可视化** —— 浏览器 / 数字形象 / artifacts。
3. 与其它实机交互场景 (教学 / 演讲 / 讨论 / 机器人躯体) 的差别: 见 KD6。

## Key Decisions

### KD1. 判据 = "私有 → 共享", 不是"有人在看"

见"核心目的与判据"。这条决定所有下游取舍: 任何"为了让观众看懂"而做的设计都是走偏,
因为**行为发生了本身**才是载体。

### KD2. 弹幕 = background 感知, 用现成原语, 不新增 nucleus

`Priority.BACKGROUND = -1` 的语义是 **"永远不能挑战成功任何当前注意力"**。而
`ImpulsePrimitive.background_notice` (= `BACKGROUND + notify`) 的 docstring 用例写的就是
**"日志 / 监控 / 环境信号 —— 不重要到要打断 ghost, 但下一轮思考应该能看到"**。

所以链路是: 开源库监控直播间 → node → 发一条 background signal。**不需要新 nucleus,
可能连新 SignalMeta 都不用。**

**但: 投递策略 ≠ 输入治理。** mindflow 解决"不打断", 解决不了"弹幕无上限"。**弹幕的
聚合/限流/去重必须有人认领** (见"未认领"节)。

### KD3. 直播记录 = 对外轴上的两列追加表, 不做时间戳

位置: `.ai_partners/` 的**对外轴** (`.ai_partners/blogs/` 的兄弟), **不放根目录** ——
根目录是代码表面 + 项目自述, 不属于这个轴。必要时给它一个 `GROUND.md`, 根 `GROUND.md`
的 `pins` 会自动把它索引到根视图。

形状: **两列追加表** —— `commit` / `视频链接`。一次直播覆盖的是一段 commit 区间, 记范围
或标明它是该场尾帧。

**明确的否决 (2026-09-18)**: 不做 **t0 / 时间原点绑定** (把视频内部时间与 MOSS 事件
时间戳对齐, 以便"指进视频里")。人类判断: **维护不动**。代价是记录不可 seek —— 概念期
的合理取舍。

**它值得存在的硬理由**: 它**免疫腐烂**。文档会腐烂是因为它断言"现状"; 直播记录只断言
**过去发生过的事**, 与 git history 同类。所以 append-only 即可, 不需要周期性治理。

### KD4. 可视化粒度 = "行为的可见性", 不是"信息的可理解性"

不假设观众会看到细节并看懂 —— 没人感兴趣。**主要载体是"可观测的行为发生了"本身。**
这砍掉了整个解释层 (解释留给事后: 记录 / 博客)。

**但要保留一半**: 行为要可见, 行为就得**有边界** —— 有开始有结束才叫一个事件。
`file_editor` 的形状是对的粒度 (动作 + **预计算的 effect**, 决定之前 diff 就可读), 但
理由不是"好读", 而是它把行为变成了一个有边界的事件。**bash 输出没有边界, 所以那一格
必须人为切一刀 (命令 + 结束)** —— 否则它不是"行为的可见", 是"终端的可见"。

### KD5. 冷场不哄观众 —— 照实播

直播开发的本质是**开发**。长任务等待不是靠内容去"填", 而是**播真的**: 有一条
**非依赖开发线**释放开发者的等待时间 (顺手打个游戏, 一路子屏投到某个小窗)。

推论两条:
- **广播画布必须是多槽位布局** (主工作区 + 小窗), 不能是全屏画面。
- **"非依赖开发线"是工作组织概念, 不是广播概念** —— 它约束的是**人的日程**, 不是代码。
  它是 `.ai_partners/features/.discuss/2026-09-17-features-system-preparation.md` Part 8
  那个"伪并行"的**正面表述**: 以前它是生理成本的来源 (脑里 6-7 条轨), 现在它是设计原则。
  这条值得单独记住, 因为它是整个 feature 里最"人"的一条。

### KD6. 与其它实机交互场景的判据差别 = 剧本的有无

- 教学 / 演讲: 内容事先成形, 判据是"理解 / 表达" → 要放慢、解释、重复。
- 讨论 / 辩论: 立场事先成形, 碰撞就是内容 → 要多条可见的声音。
- 机器人躯体: 观众共处一室, 交互是身体性的 → 判据是延迟与物理在场。
- **开发直播: 结果对参与者自己都未知** → 无法编排, 叙事只能从过程里**事后重建**。

**推论(硬)**: 在这个场景里, **"记录"(KD3) 是唯一的叙事载体**。没有它, 开发直播只是
没有索引的原始素材。所以直播记录不是"顺便带出的概念", 它接近骨架。

### KD7. 交付物是可复现的配方, 不是散文

"告诉其他人怎么用 MOSS 直播开发" —— 如果写成一篇 howto, 它就是今天讨论里刚判过的那种
会腐烂的东西。**它应落在 `moss skills` / howtos 那类可执行条目上** (与 `moss-skills`
同形)。散文版的体系没有维护力。

### KD8. 执行方式 = 收敛, 不是发散

1. **不造新概念**, 只把已有的从私有改成共享。有 owner 的只做接线 + 验收, 不重写。
2. **只补真缺口** (见下节)。这是执行纪律 —— 否则这个 feature 会膨胀成把所有依赖重做一遍。
3. **先立最小可播闭环**, 不是全量: 语音对话 (听说) + 弹幕入 + 一块承载 + 直播记录一行。
4. **验收是一次事件, 不是一组 commit。** 依赖没就绪它就不该开工 —— 执行节奏天然是
   "等依赖 + 补缺口", 中间不该持续投入。

## 缺口 (本 feature 自造)

| 缺口 | 性质 | 备注 |
|---|---|---|
| 直播间 node (弹幕 → signal) | 新 node | 按 KD2, background 优先级, 用现成原语。`nodes/sensors/` 是空的, 感知侧槽位预留 |
| 行为可见的粒度切口 (bash/终端) | 新 node / 新面 | 按 KD4 必须人为切边界。⚠️ `nodes/os/terminal/` 的 scaffold 已出现 (untracked, 2026-09-18, 含 `store.py` + `card.py`) —— 归属与边界待与人类确认, **别重复造** |
| 直播记录 | 新产物 | 按 KD3, 对外轴, 两列追加表 |
| 配方 (体系) | 交付物 | 按 KD7, skills/howtos 形态 |

## 未认领 (显式 cut scope, 不许含糊)

- **披露边界** —— "主题内容都共享"**不能是"全部共享"**。模型上下文里有 `.env` / API key /
  工具输出里的密钥 / 别人托付的私有信息 / **模型自己的推理轨迹**。公开直播是**永久**的。
  需要一条"必须投射 / 必须扣留"的边界, 且**由投射层强制执行** (靠人记着会漏)。接
  `safemode` / `warrant`。
- **弹幕限流 / 聚合** —— 见 KD2。
- **中途入场者的上下文重建** —— 观众不是从第 0 分钟开始看的。第 3 小时进来的人需要一条
  "现在在做什么"的入场引导。这是"在飞态"的第二个用途 (第一个是展现代理活动)。

## Exploration Paths / 已否决 (含偏航记录)

- **偏航 (最易再犯): 一度把观众判成"模型"** —— 把问题读成"开发内部的协作损耗"。
  真相是**外部的观看者**。记下来, 因为这个误读来自一个合理的直觉 (MOSS 的观察面全是
  pull, 确实缺"正在发生"), 但它指向了完全不同的设计。
- **否决: t0 / 时间原点绑定** (见 KD3)。
- **否决: 用高优原语 (`broadcast` / `inject`) 送弹幕** —— 弹幕是 background, 不是必达广播。
  选错会把直播间变成"永远在打断 ghost 的输入源"。
- **更正: qt_screen 当作屏幕载体** (见"依赖")。
- **否决: 把本 feature 当 stage gate** (见 Motivation)。
- **否决: 一开始就为"可 seek"设计记录** —— 与 KD3 的 t0 否决同源: 概念期不为未来的
  检索能力付维护成本。

## Implementation Notes

- **最大风险是 silent todo。** 8 个依赖全在飞, 极易写着写着把缺口糊过去。所有"等它 /
  不归我"必须在本文里显式成文。
- **`background_notice` 的边界 (它自己的 docstring 写了)**: quiet 系统 (无 attention) 下
  `notify` 走 default 路径会**新建一个 attention** 成为焦点 (低优, 任何信号可抢)。对
  直播间这大概正是想要的 —— 没人说话时弹幕自己冒出来 —— 但它是明确副作用, 不是意外。
- **`Priority.BACKGROUND = -1` 的语义比"闲时加入"更强**: 是"连挑战的资格都没有"。
