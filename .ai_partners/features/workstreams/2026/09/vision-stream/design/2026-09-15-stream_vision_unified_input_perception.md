# 流感知：把视觉输入统一成一个协议地址

**日期**: 2026-09-15
**来源**: 人类工程师与 DeepSeek Flash 的碰撞收敛（起点是"把屏幕截图能力建好"）
**归属**: vision（**不是** os control）

## 问题

vision 到目前为止的形态是"每台设备一个 node，node 自己采集、自己交给模型"。它的隐含代价是：
**MOSS 每接入一种视觉来源，就要写一份采集集成。**

而屏幕截屏、摄像头、OBS 直播、第三方视频流、网页流、另一台机器的画面 —— 这些是同一类东西：
**一路可被看的视觉**。把它们当成 N 种能力去分别实现，是把问题的形状看错了。

## 核心洞察

**一个协议地址 = 一路可开的视觉。**

ghost 不需要"MOSS 支持某台设备"，它只需要**被告知一个地址**。采集（推流）是别人的事，
MOSS 只做消费者。于是：

- **推流模块**（producer）：camera、屏幕截屏、OBS、IP 相机、另一台机器的 ffmpeg。
  它们的共同产物是**一个地址**，不是一个 SDK。
- **流感知 node**（consumer）：对地址开视觉。
- 两者的契约只有一个：**地址**。

这个机制的真实价值不在截屏，在于**视觉接入从"N 种设备集成"塌缩成"一个地址协议"**。
摄像头与屏幕截屏因此不再是两种能力，而是两个推流模块 —— 播放路径完全相同。

## 核心决策

### KD1 这是输入感知，不是输出流

node 只消费，**永不产出流**。ghost 监听流获得流内视觉，而不是给别人播流。

模型面不需要实时画面，只需要**历史视觉记录**（"模型看过哪些图"）—— 一个随机端口的
aiohttp 就能承载，不需要直播基础设施。

### KD2 地址即接口

地址是**身份**，不是命令参数：它在 node 启动时通过 argument 绑定（见 KD4），
命令面因此无地址 —— `capture` / `watch` / `status` 只操作本 node 绑定的那一路。
label 是人/模型好读的别名（地址的 read-back 身份）。

### KD3 归属 vision，不是 os control

**本决策取代 `moss-os-control` 的 KD4**（"屏幕截屏 = OS 原生能力的控制面 → 归 `nodes/os/`"）。

按能力域切分时，"屏幕截屏"的实质是**感知**，不是 OS 控制。os 域若将来还需要保留什么，
它的身份是"**一个把屏幕推成地址的本地推流模块**"（producer），而不是"截屏能力"。
截屏能力由"流感知 node + 屏幕推流模块"组合而来。

### KD4 非单例：一个 node = 一路流

`singleton: false`；argument 传入 **流地址 + label + 空闲回收窗口**。启动即连流。

理由：

1. **授权闸口落在节点打开**。流感知有实时性 —— 动作级授权（"再问一次能不能截图"）没有意义，
   来不及也说不通；有意义的只有"这个 ghost 是否被允许拥有这一路视觉"。per-stream node 让
   授权点与节点打开重合。singleton hub + `open(address)` 会把闸口推到动作级。
2. 与 vision 家族契约一致（一个 node = 一个源；多源 = 多实例）。
3. 生命周期即占用：node 起 = 流连上，node 停 = 流断开，模型与人读得出来。
4. `look` 阶段的重感知循环拿到独立进程：可杀、可限资源、崩溃隔离。

代价（已知、接受）：N 路流 = N 份 channel 表面进 context，token 线性增长。
缓解手段是把单实例命令面压到最小，并用 KD10 的人开关把这些表面移出 context。

### KD5 ingest 只解码，不压缩

node 自己起的 ffmpeg 子进程只负责**解封装 + 解码 → JPEG**，不做缩放。

- ffmpeg 是子进程 = 隔离点：流坏了只死子进程，node 事件循环不受影响。
- node 侧不做解码：切 JPEG 边界、留尾帧。
- **上游推流者的参数不归我们控制**（第三方直播的分辨率/码率由对方定），但解码之后的像素归我们 ——
  所以能不能压从来不是问题，"什么时候压"才是（KD6）。

### KD6 发射点阈值门：达标直通，超标才转码

压缩发生在**发射点**，不发生在 ingest：

```
尾帧 (JPEG bytes + dims + ts)
   ├─ 出模型：dims ≤ max_edge 且 bytes ≤ max_bytes → 原样直通（零成本）
   │                                              否则 → 解码 → 缩放 → 重编码（仅此一帧）
   ├─ 给人看：原样（源可被浏览器直接播时优先直连源）
   └─ 落盘 export：原样
```

理由：

1. **稳态零成本**。不做每帧缩放；capture / watch 每轮最多发一张图，只处理这一张。
2. **小流完全不转码**。上游本来就在发小尺寸，或路径是 MJPEG（推流者自己的 JPEG 字节）
   时，可以一路直通到模型，node 连解码都不必。
3. **按出口分规格成为自然**：同一份尾帧，模型入口过阈值门，人看与 export 拿原图，
   不需要两路 ffmpeg。

判据用两个而不是一个：**像素尺寸**（决定 token）与**字节数**（决定 base64 体积与 provider 上限）。
尺寸在连接时即知（ffprobe），字节是 `len(jpeg)`。

**数字是消费者的知识，不是生产者的。** 约束来自"谁在读这张图"（模型 / provider），
所以常量声明在 LLM adapter 旁并注明来源，node 侧只作为可配参数（默认取该常量）。
换模型时数字跟着消费者走，node 不改。见 vision KD9。

### KD7 只读尾帧，不缓存，不重放

`capture` 与 `watch` 都只读内存里的尾帧。不做历史缓冲、不做重放、不做列表/翻页命令
（它们本身也是 token）。流 30fps 不会导致推 30 张图。

附带效果：**停滞问题只属于热会话**。冷拉取拿到的必然是新鲜帧，构造上就"陈旧帧伪装成当前画面"
这一整类故障。热会话下才需要停滞判定（超过 N 秒无新帧 → 状态 stale，模型可读）。

### KD8 refresh_meta 零 I/O

channel 的 meta 刷新路径上不得有任何阻塞 I/O：不连流、不解码、不做回收判定。
连通 / 断流 / 停滞全部只体现为内存里的状态字，由后台子进程或协程更新。

这是把"零耗时"从愿望变成约束的唯一办法 —— 也让流故障通过 channel 短路
（refresh raise → failure）自我表达，而不是拖慢每一轮模型思考。

### KD9 会话由消费者驱动

流连接是**惰性短命会话**：有请求就热，空闲回收窗口到达就断流。没有消费者 = 没有采集。

这沿用 vision KD10 的纪律（context 不得驱动采集率）并把它推广到"存在性"这一层。
代价必须摆明：**空闲回收与"capture 零延迟"不可兼得** —— 回收后重新拉流要重付关键帧等待
（本机 0.5–2s，取决于推流者 GOP）。对模型无感，所以回收窗口按使用节奏给（几十秒到几分钟），
不必设得太短。

### KD10 人类面 = 实时镜像 + 人的开关

单个随机端口 aiohttp 单页，三个作用：

1. **投放流本身**（小窗/全屏）。源可被浏览器直接播时优先直连源（零 node 成本）；
   否则复用尾帧。
2. **下发模型看过的图**（WebSocket 推 base64，**不落历史**）。历史图片存不起，
   拉接口也没用 —— 人要看的是"此刻模型在看什么"，不是档案。
3. **一个开关**：人关闭 → node 收到 → `available` 返回 False（命令从模型表面消失）
   + notice 报状态变更。

**打开网页 = 成为消费者 → 会话保持热；关闭 = 空闲回收生效。** 人的在场与采集的存在性耦合，
占用因此诚实。

开关有**两重价值**：隐私否决权，以及把这些 channel 表面移出 context 的 token 开关。
它对应 screen-node KD10 的"人机双主权"，但比它更强：模型是默认第一公民，人保留一票否决。

### KD11 授权不在 node 内实现

node 代码不做任何授权逻辑。授权机制未来统一在 **run node 侧**做（与 KD4 的"闸口落在节点打开"一致）。
本实现不预留授权接口，也不发明局部方案。

## 拒绝的方案

| 方案 | 否决理由 |
|---|---|
| 帧走 dynamic context 推给模型 | vision KD1 已否决：dynamic context 瞬态，陈旧帧会伪装成当前画面入史 |
| 消息层自动压缩 | 静默改图（KD9 明确反对）；且消息层看不到这一帧要去哪个出口 |
| ingest 时每帧缩放（`-vf scale`） | 没人看的时候也在付缩放的钱；且尾帧被降级，人看与 export 一并受损 |
| 低延迟协议（WebRTC / NDI / HLS 优先） | 没有实时消费者 —— 没有人在盯着画面看，延迟不构成约束，只剩依赖重量 |
| 历史图片存储 + 拉取接口 | 存不起；且"人知道模型看过哪些图"用实时下发即可满足，档案没用 |
| singleton hub + 每地址一个子 channel | 授权会落到动作级（`open(address)`），正是本机制要避开的 |

## 协议

有了统一的 ingest 路径，协议选择不是实现成本问题，而是"第一批值得测与写文档的是哪些"。

| 协议 | 位置 | 理由 |
|---|---|---|
| **MJPEG over HTTP** | 第一批 | camera 与屏幕推流模块的将来形态；推流者自己的 JPEG 可直接直通，理论零解码 |
| **RTMP** | 第一批 | 推流世界的事实标准（等价于 HTTP 的位置），OBS/ffmpeg 人人会推 |
| RTSP | 第二批 | IP 相机标准 |
| SRT | 第二批 | 跨机器/弱网最稳（本机 ffmpeg 已带 libsrt） |
| HLS / UDP-TS | 按需 | 通用但延迟高（无所谓）；局域网组播 |
| WebRTC / NDI | 排除 | 依赖重量不成比例 |

## 已知缺口（实现前提）

1. **`run_node` 没有参数通道。** Matrix API 只收 `target` + `extra_env`；模型面（nodes channel）
   只有 `run_node(target)`。CLI 的 `moss nodes run <path> -- --addr ...` 是通的，但**模型驱动的
   spawn 路径走不到 argv** —— 于是"ghost 拿到地址开一路视觉"今天做不到。这是 bug，须先修，
   落点与 KD11 的授权机制同一处。
2. **图片约束常量在 MOSS 中没有声明处。** `Base64Image.from_pil_image` 无尺寸/质量/字节参数，
   message 与 llms 层搜不到任何约束常量。vision KD9 已判（语法糖 + 传参 + 默认值 + 常量落 adapter 旁），
   流感知 node 是它的第一个真实消费者。
3. **camera 的 `singleton: true`** 与"多摄像头 = 多个 node 实例"的家族契约矛盾。

## 扩展点

- **look（主动视觉）**：条件命中由身体主动返回 signal。需要连续感知 → 恒热会话。
  实现位置待定（node 内可插拔条件 vs 独立消费者 node），判据是**响应性**：
  capture 的延迟不得被 look 拖累。
- **重感知复用**：人脸识别、视觉模型解析等后台逻辑可挂在同一路流上（检测到就打招呼一类）。
  所有视觉动作拿到的图都带 text 描述与图时间。
- **出向**：其他 cell（数字人、显示设备）要消费同一路时，落点是 MOSS 的 `session.stream`
  字节流原语，**不是 RTMP**。入向用外部媒体协议，出向用 MOSS 原生 —— 两条流是不同的路。
