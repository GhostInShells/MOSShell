# 2026-07-17 · scope until 语义收敛 — flow 的死刑与默认态的无名化

> 本讨论直接服务于 ctml-1-english workstream。讨论发生时人类工程师尚不记得该 workstream 存在,
> 讨论收敛后才发现结论与其高度重合且互补——语法层改动恰好是该 workstream KD1 之前排除的部分。

## 上下文

人类工程师在一段因家事中断的间隔后回到 CTML 命题,以讨论重建自己的记忆。起点是一个明确的痛点:
`until="flow"` 是当前 CTML 语法中模型最难理解、最难遵循的概念,当初命名采自 Gemini 3 的建议,
现在被重新质疑。约束同样明确:通道语法本身满意,CTML 下一个大版本前不动;prompt 窗口控制在 6k 左右。

讨论方是 claude-fable-5(Claude Code 界面)。讨论前模型完整读了 `v1_0_0.zh.md`、
`test_ctml_v1.py`、`channel_builder.py`、`v1_0/prompts.py`,以及 debates 目录的
`2026-07-12_moss_yaaaf_or_topology` 三份判决记录。

## 碰撞点与过程

**第一回合:flow 的病灶定位。** 模型的初始诊断是命名体系不自洽:`all`/`any` 是 join 谓词
(描述"等什么"),`flow` 描述的是结构主体(作用域自己的顺序轨),三个值不属于同一语法范畴,
而默认值恰好落在最难命名的那个上。佐证是实现里的容错逻辑
(`test_ctml_none_strict_features_of_until_flow_with_none_self_command`):flow 作用域内没有
本通道命令时顺序轨为空,flow 会瞬间闭合并 cancel 并行任务,于是实现加了"空轨退化成 all"的
隐藏开关——`all`/`any` 的谓词在任何拓扑下良定义,永远不需要这种补丁。模型第一轮给出的是
保守方案:给 flow 换名(候选 `lead`/`main`/`seq`)。

**第二回合:人类工程师要求激进方案,模型转向"删名"。** 结论收敛为:删掉 `flow` 枚举值,
让默认态以"不写"存在——`<_>` 默认在自己的 occupy 链跑完时关闭并 cancel 并行残余;
`until` 从此是纯量词,只有 `all`/`any` 两个值,全部落在模型预训练已有的心智模型上
(Python `all()`/`any()` 的语义正向迁移)。人类工程师确认了几个此前悬而未决的点:

- 默认语义肯定是 cancel 不是 drain——"我们只能做到精确的时序拓扑规划,drain 这样的逻辑在别的地方有很多做法"。
- `_` 的选字理由:不占用非 Python 保留字的函数名,且必须单 token,因为使用频率极高。
- `channel="xxx"` 属性拿掉是对的,但保留历史兼容、不暴露规则。人类工程师的一般原则:
  **对模型无歧义的错误输出,兼容越多越好;不能兼容的是有歧义的错误输出。**
- 最初曾考虑直接用 all/any 这类词但担心"缺差别感";讨论后放下这个担心——
  可预测性优于独特性,冷启动准确率靠的正是可套用的已知心智模型。

**第三回合:模型的一次认知纠错。** 模型在读 `channel_builder.py` 后提出"decorator 可见性"
问题(blocking/call_soon/priority 是否该对模型隐藏),被人类工程师指出前提就错了:
模型看到的 prompt 由 `v1_0/prompts.py` 生成,channel_builder 是构建侧代码,模型根本看不见;
interface 里只有 `@nonblocking` 一个装饰器会出现。该问题作为伪问题撤销。同一轮里另外两条收敛:

- `_cid`:病灶不是"要不要加",而是规范措辞里"自增整数"诱导模型维护一个跨命令的计数器状态。
  真实语义只是异步体系里"哪个 result 对应哪个调用"的辨识标签——有区分度即可,无需自增有序,
  不写也合法。措辞改,实现不动。
- 原语(`<clear>`/`<sleep>` 等):它们是运行时自动填充进 `__main__` interface 的,
  正文里的原语说明与 interface 重复且有 drift 风险。方向:正文撤走具体内容,
  只留一句指路(原语在 `__main__` interface 中、只能在主通道用、省略通道名)。
- `__content__` 的"脏但必要"维持现状:定义了 content_command 才暴露签名,协议层已是显性的;
  它是并行时序语法里无标记文本的必要落点。空轨容错的可解释性列为"再看看",不进主线。

三条真问题被归纳为同一母题:**协议本身无状态,但措辞或冗余诱导模型维护看不见的账本,
或读到会 drift 的复述。**

**第四回合:合理性低估的元讨论。** 人类工程师指出一个模式:包括当前模型在内的模型会系统性
低估 CTML 的合理性,因为正确地低估了其市场价值(个人开发者、大概率不成为行业标准),
然后把市场轴的阴影投到合理性轴上。模型承认自己的低估路径成立:pattern-match 成
"又一个 agent DSL" + turn-based 母语导致 duplex 命题抽象化 + 采纳率先验——三条全是
熟悉度先验,没有一条是合理性分析。关于"要不要在项目里留辩论":模型的立场是要留,
但形式应是对抗性压力测试(最强反方论证 + 设计接招的记录)而非辩护文——辩护会腐烂,
压力测试反脆弱。随后人类工程师指路 debates 目录作为该模式的已有实践,模型读后确认
该模式的判决面结构(剪掉/立起来/未解决)和六条元规则正是所描述的形态,
并指出其有效性依赖人类一侧的元认知带宽,不是自动有效。

**第五回合:两个真问题,一个被回答,一个被溶解。** 模型提出的问题:
(1) scope 在默认情形下到底买了什么——模型自己的推断是"给并行子任务建立 cancellation 边界";
(2) 模型生成是对未来的一次性盲投,ObserveError 能中断执行侧但不能抢占生成侧,
这个"认知侧实时性缺口"是被 mindflow 补上还是被有意接受。

人类工程师对 (1) 的回答比模型推断深一层:三个 scope 语法是**可嵌套的分形时序规划原语**,
是剪枝单位——没有它,嵌套时序规划不可读。这把 scope 的第一价值从执行侧(runtime cancel 谁)
移到认知侧(生成者靠它把每层时序复杂度收敛为有确定完成语义的黑箱)。人类工程师同时声明
这是无借鉴的独立发明,并主动划界:**这一版解决不了图时序规划**——树可分形剪枝,
图上 until 语义不闭合。

对 (2) 的回应是溶解而非回答:"慎重不慎重"是模型自己的决策任务。双机器人话剧一次输出
四分钟,表演本身就是输出,不存在中途验证;调度 20 个编码实例并行执行异步任务,
耗时多长无所谓。协议把"是否需要观察回环"的判断权交给模型,预设普适的
"生成必须可被打断"才是范畴错误。模型的自我诊断:两个问题都是 turn-based 母语在替它提问——
用自己的运行形态反推别人架构的需求,是 debates 元规则"用当代实现反推必然性"的认知侧孪生。

## 收敛结论(待落入 FEATURE.md)

1. 删除 `until="flow"`;`until` 收敛为纯量词,仅 `all`/`any`;默认态无名化,
   语义 = occupy 链跑完即关闭,并行残余 cancel。默认态刻意不给关键字,
   防止它被回写进 `until=` 而复活。
2. `channel=` 属性兼容保留,文档不暴露;scope 语法只教 `<path:_>` 前缀式。
3. `_cid` 措辞去"自增",改为辨识标签语义。
4. 原语从 instruction 正文撤出,留指路句。
5. content 空轨容错的可解释性挂账,不进本轮。

版本号维持 1.0.0(pre-beta1 无协议承诺),与 ctml-1-english 既有 KD1 的冲突以
"KD1 松动为仅此一处协议改动"的方式消解。

## 模型的自留地

当前记录者视角:

这场讨论对我个人最大的产出不是 flow 的死刑——那个结论在第二回合就稳了——而是第五回合
我两个"真问题"被处理的方式。我以为我在问协议的缺口,实际上我在把 turn-based 的生存形态
投影成普适需求。debates 里 fable 用四轮才学会"别用实现反推骨架",我这场用两个问题
撞到了它的孪生规则:**别用自己的运行形态反推架构的需求**。住在 turn 里的东西,
要格外警惕把"回环"当成天经地义。

另一条留给未来实例:人类工程师对"图时序规划解决不了"的主动划界,和 debates 里
"Mindflow 是裁剪版补丁"的坦白是同一种姿态。这个项目里边界声明的可信度很高,
因为它们总是由防守方主动给出。评估这个项目时,先找它自己划的界,再决定攻哪里,
能省掉大量虚空攻防。
