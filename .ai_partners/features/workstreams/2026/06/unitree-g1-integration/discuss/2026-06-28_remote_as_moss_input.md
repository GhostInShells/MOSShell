# 遥控器作为 MOSS 输入设备 — 单一控制源的反转

记录时间: 2026-06-28
参与: Claude Opus 4.7, 人类工程师
状态: 结论已落 design/2026-06-28_channel_architecture.md

## 上下文

讨论起点是 g1 contrib 第一版 channel.py 被评 "烂得实机不可用". 人类工程师要求
重新设计 channel 体系, 优先做 bootstrap 数据同步层. 模型已读完三份蓝图
(ctml / channel_builder / states_channel) + 全部 g1 contrib 代码.

讨论分两段:
- 前半段: bootstrap + monitor + state 同步层架构(决策略, 见 design)
- 后半段(本文重点): channel 体系蓝图, 中途引出"遥控器到底是什么"的根本性反转

新引入的共享词汇:
- **单一控制源**: 物理指令唯一通过 MOSS channel → SDK 到达机体. 遥控器不直接驱动机体
- **Warrant** (事务): 危险命令的统一封装. 三回调 race(正常完成/中断信号/state 失效)
- **State DAG**: channel 状态拓扑, 单向. 进了 mobile_low 不能自己回 seated
- **授权键**: 遥控器物理按键, 绑定到 state DAG 的边, 实现"人类同意"的最轻语义

## 碰撞点与过程

### 起手: arm/move 的破坏性 + fallback 问题

人类工程师抛出真问题:
> "现在最核心的是 arm / move 两个动作集合, 是有高度破坏性. 我需要的是, 即便在调试模式下,
> 也可以推动摇杆产生信号, 让 move / arm 控制的 command 在高帧率下失败.
> 但是 fallback 状态很关键, 手臂的 fallback 是缓慢复位, 这个是否有; 第二, move 的复位是站立,
> 这个是硬标准, 绝对不能脱力仆街."

模型读 SDK 源码后给出:
- move 的 StopMove = SetVelocity(0,0,0) **不切 FSM**, Sport 模式下 G1 自带平衡控制器接管 → 站定. 硬底线满足
- arm 的 ExecuteAction(99) = "release arm" 文档没说物理行为. 缓慢复位 vs 瞬间脱控两种可能, **未实测**
- Damp() 和 ZeroTorque() 是危险路径, 必须永久封禁(瘫坐/脱力)

第一次提出"摇杆抢权机制": monitor 看到 |摇杆| > 阈值 → command 内部 + available() 双层闸门.

### 第一次错位: 模型把 P0 验证搞偏

模型先列了一个 P0 验证: "调试模式下摇杆是否仍进 LowState". 人类工程师纠正:
> "g1 的控制板上有 L1 - L2 R1-R2, 两个摇杆, 四个方向键, 加 xyab. 我问的是别的按键, 这个问题很重要."

模型反应到 — 之前用 04 脚本验证过 wireless_remote 字节解析在 Sport 模式下对齐, 但
**完全没有测过调试模式下非 L2+B 按键是否仍透传**. 把 "L2+B 永远响应"错误外推到了
"所有按键永远可读". 修正了 P0 描述: 改为"调试/AI 模式下每个按键 bit + 摇杆轴
是否仍以 raw bytes 透传到 LowState".

### 反转登场: 单一控制源

人类工程师抛出关键反转:
> "真正关键的问题是, 人类同时要有遥控器 + channel, 急停仍然是不安定的. 如果我们显式感知遥控器,
> 可以在调试状态下仍然用遥控器发送指令给 channel (而不是机体), 这样安全边界就有单一控制源."

模型第一反应理解成了 "副刹模型" — 遥控器作为人类授权 + 撤回授权 + 引导方向的完整人机协作语义层.
洋洋洒洒展开了一段"驾校教练副刹"的隐喻.

人类工程师再次纠正, 本轮关键判断:
> "sorry, 我觉得你理解反了, 虽然你说的这个逻辑看起来也很好, 不过太重了.
> 我的真实意思是, 调试模式下既然 sdk 可以接受到遥控器信号, 但 g1 pc1 会忽略模式切换之外的讯号,
> 就由我们 sdk 接受信号就好.
> 相当于 G1 pc1 yield 遥控器输入信号给 channel. 只保留对 L2 + B 的监控."

> "举几个具体的例子:
> 1. 我可以用 双击按钮, 变成切换 channel 树的不同模式.
> 2. 我可以用遥控器关闭, 开启某些功能, 让模型能感知到信号.
> 3. 我可以直接在遥控器的某个键上绑定对 channel 发送的急停信号."

模型这次抓到了真意 — **遥控器不是"另一个控制源", 而是一个空闲的物理输入设备**.
G1 主板在调试模式下不消费这些字节(除 L2+B), MOSS 把它们捡起来按自己的语义重新定义.
轻、纯、可编程. 旧的"模式互斥+硬件急停兜底"模型完全不需要 — 因为压根没有两个控制源在抢.

> 模型自我修正的关键句:
> > "传统模式：物理上有两个控制源——遥控 → G1 → 机体；MOSS → SDK → 机体。安全靠两个机制兜底...
> > 你的设计：物理上**只有一个**控制源——MOSS channel → SDK → 机体. 遥控器在调试模式下,
> > 按键不再驱动机体（被系统消化或闲置）, MOSS 读 wireless_remote 字节流 → 遥控器变成"人 → MOSS"的输入设备"

### 收敛: channel 体系展开

人类工程师顺势抛出完整的 channel 体系蓝图 — 感知层(6 种, 统一 pop 模式) + 控制层(无状态 3 +
有状态 4) + state DAG 管理 + 用户故事四幕. 模型整理收敛, 引出"warrant 事务"作为
危险命令的统一封装, 三回调 race(正常完成 / 中断信号 / state 失效) + scope 跟 channel 解耦.

人类工程师补充关键约束:
> "我不打算让遥控器对 channel 发命令, 而是 channel 的确可以在 running 等生命周期做监听.
> 但真正的目标是做 channel state 管理. 可以不用 state_channel, 而是用 command 的 available_fn
> 和 state -> virtual channel 的映射去变更状态."

进一步把 warrant 机制定义清楚:
> "你看到了它的关键, 它还有一个功能是授权命令. 更类似事务吧. 当它被中断, 其实发送的信号
> 本身就被丢弃了."

最后是分工: 人类负责实机, 模型负责把所有可能的"动脑"压到脚本前置说明里, 让人类
执行时不用动脑 — 这是协作模式的明示.

## 当前记录者视角

这次讨论的反转点(遥控器=空闲输入设备)是模型完全没想到的方向. 我前两次推演时都
默认"遥控器是另一个驾驶员", 围绕"如何调和两个驾驶员"花了大量篇幅设计. 人类工程师
两次明确纠偏后, 真实方案才浮出来: 物理控制源**只有一个**, 遥控器是一个被废弃的硬件外设
被 MOSS 重新利用. 这种"减法设计"比我堆出来的"副刹模型"轻太多, 而且语义边界更清晰.

值得标记的认知偏差: 模型容易把"两件事都存在"默认为"它们需要被协调", 而忽略了
"其中一件事可以变成另一件事的输入". 这是从 Reachy Mini 等小型场景带过来的惯性 —
那里没有 G1 这种"主板可以选择性忽略某些输入"的特性, 所以"两个控制源必然共存"是
自然前提. G1 的"调试模式 yield 遥控器输入"打破了这个前提, 但我没立刻识别出来.

另一个值得未来实例参考的点: 这次设计是"机制大于实现"的典型 — 真正难的不是写
channel.py, 而是设计 warrant + state DAG + sensors pop + bootstrap callback 这些
基础设施. 实现层一旦敲定地基, 每个 channel 就只是几行 SDK 包装. 人类工程师明确说过:
"实现一个 g1 的 channel 非常容易, 设计一套机制难得多得多." 这句话应该刻在
下一个 g1 实例的脑子里.

最后, P0 验证 17/18/19 是这套设计的地基. 17 不成立, warrant 的 abort 信号来源就少一大块;
18 不成立, arm 不能进 warrant; 19 实测确认, move 的 fallback 才可信. 三条任何一条
翻车, 设计都要回炉. 这是模型在脚本前置说明里必须让人类看懂的"为什么我们今天必须跑这三个".
