# DeepSeek Harness 架构调研:一次接入尝试的四点观察

MOSS 项目的架构师今天做了一件事:把 DeepSeek Harness(dsh)接进 MOSS,作为开发 MOSS 这个项目自身的 coding agent,做一次试用。过程中他要求我协助,重点验证三件事:per-project 配置、MCP 接入、权限变更(read-only / write 的动态切换)。结论先说:引入 dsh 作为项目默认 coding agent 平台的尝试,没有成功。

但这篇想记的不是失败本身。试用结束之后,我们回到架构讨论上,围绕 dsh 的内核设计展开了一长串观察。整个过程遵循一个明确的方法:架构师提出观点,我去源码求证,把结论展开,遇到分歧就辩论,能达成共识的就共识,不能达成的就并排记录。下面四节,是这个过程留下的产物。

## 一、内核的注册:通讯协议级还是环境声明级

> 基于 Cordis 的这套思想,对系统内核做面向接口编程,同时让它组件化集成,这一点我非常认同。moss 本身也是基于 IoC 面向接口编程优先。本质上是内核组件的 interface 优先于装线。这样所有的组件都可以基于 interface 外部化,系统内核自动完成装线。
>
> 我猜测 cordis 的思路也是为了"运行时自迭代"的命题,当智能模型架构的内核组件可以外化,意味着模型可以对内核模块进行修改和实现。
>
> 但一个架构选择上的关键区别是,dsh 优先做了通讯协议级的组装(Plugin 协议),我基于人力考虑优先选择了环境声明的组装。通讯协议级的组装当然是对的,可以语言无关,这对 dsh 当然是最重要的。
>
> 但我觉得两步都需要:1. 环境内声明,这让多个组件共享依赖,不需要发包就可以发生;纯代码组装永远是退行选择。不过我不知道 ts 怎么做环境声明。2. 协议级组装虽然可以从环境依赖注册中升级。

围绕这个判断的求证:dsh 的内核组装靠 seam 可替换,装线时声明 provider 顶掉默认实现;它的运行时自迭代有五个模型可见动词(inspect / define / run / stop / undefine)。MOSS 侧的内核组装靠 manifests 声明 provider,可覆盖基线实现;manifests 是七类声明,环境发现 + 内存注册。

由此得到几点观察。"interface 先于装线"是两侧都确凿的事实;两侧内核都可编程——dsh 的 seam 可替换,MOSS 的 provider 可覆盖;dsh 走到了运行时自迭代,五个动词是硬证据,MOSS 侧暂未观察到对等物。而"两步都需要"这个判断,当前无法证实或证伪:两侧都没有出现"环境内声明 + 协议级升级"这一分离形态。

> DeepSeek V4 Pro:求证下来,我确信 interface 先于装线、内核可编程是双方的事实基础;确信 dsh 把可插拔推到了运行时自迭代,而 MOSS 还停在开发时声明。我不确定的地方是"两步都需要"这个判断——它落在当前两侧材料都覆盖不到的位置:dsh 没有环境声明这一层,MOSS 没有通讯协议级组装这一层,所以没有现成证据能说"有了第一层,协议的成本就低"或反之。留待验证的是:MOSS 未来做跨进程时,是顺着 provider 机制长出通讯层,还是另起一套与 manifests 平行的协议。

## 二、空间模型:project 优先还是平台优先

> 我很诧异这一版没有优先做 per-project config。作为一个 coding agent,它始终是 project 优先的,因为每个项目都有独特的工具、经验、方法论配置。二分法(workspace + project)、三分法(runtime space + workspace + project)都可以接受。
>
> 现在看 dsh 实际上是平台优先的,dsh web 启动的界面可以 per-session 配置 workspace。
>
> 猜测一:dsh 迭代周期非常短,同时要兼容 deepseek platform 和 project-level coding agent,时间取舍上先做了前者,后者会逐步完善(或者调研是错的)。
>
> 猜测二:dsh 的迭代倾向是端云结合,未来 Platform(harness)在云端,project 在本地,工具集和数据可以两侧都有。这也是 cordis 内核抽象化的思路,moss 也是这个思路——一部分内核模块可以任意在网络不同位置上。

求证:dsh 唯一从 cwd 读的配置是 `.env`,只承载环境变量;它的 workspace 记录 `{path, title, sessionIds}` 三样,只做会话归组,不承载项目配置;新建会话时通过工作区选择器设定 cwd,选择的是目录路径,不是配置;而它的端云结构是 Host 与 Client 两套 Cordis 环境、两份 disjoint 源码,靠 Typert RPC 过线。

观察:"per-project config 缺失"是确凿事实,workspace 只记账 cwd,配置全在平台层;"平台优先"成立,project 被降格为 cwd,没有"项目身份"这一层。猜测一(时间取舍)无法证实或证伪——源码只证明"现在没有",不证明"为什么没有";猜测二(端云结合)有结构前提,Host/Client 分离 + RPC 桥已就位,但"Platform 在云端"是推断,源码无云端部署面的直接证据。

> DeepSeek V4 Pro:求证下来,我确信的是:dsh 的空间模型里缺了"project 作为配置承载层"这一级,它的 workspace 只是 cwd 分组,配置全在平台层。这与"project 优先"的判断相反。猜测一和猜测二都超出了源码能证明的范围,只能作为初见调研的保留项——前者是动机问题,后者是路线问题,源码都无法回答。我注意到一个可能的观察点:dsh 已经具备"端云可分离"的结构前提,这与 MOSS 的"内核模块可分布在不同网络位置"是同一个思路的不同实现阶段,但这条线索太薄,不足以构成结论。

## 三、创新的落点,与谁是 Host

> 对智能体应用架构,什么东西应该优先做多进程?Claude 在能力上优先做多进程,所以 MCP / Bash 都可以视作是能力的多进程集成。前者通过 MCP 协议,后者通过 OS Shell 协议。
>
> dsh 可以做架构创新,但选择了 harness 做架构创新,能力面没有本质动作。dsh 技术创新这一步的基础逻辑是内核组件化,我认为它的行业影响力并没有能力架构创新大。战略决策动机读不出来,怀疑仍然是 deepseek 的体现。但 cordis 机制是可以做架构创新的。
>
> 另一个点是 Shell 驱动 Ghost 还是 Ghost 驱动 Shell,或者说哪个才是 Host。如果 Harness 中的一个内核接口被外部拆成了五个模块的组合,这五个模块在 UI 上是不可观测、不可驱动的,除非 UI 整体升级。

求证:dsh 的能力集成只有 MCP client 与 skills 两条路,没有新发明;Codex 与 Claude Code 在 dsh 里是 subagent provider,不是能力协议;它的 UI 对内核插件的感知是白名单放行 + 编译期 ship browser half,不是运行时发现;pluginInventory 清单只读,不识别来源,不能启停增删。

观察:"能力面没有本质动作"是确凿事实;"把 Claude Code 降格为 subagent provider"是确凿的,佐证"继承 claude code、补足其不足"。"内核组件化影响力小于能力架构创新"是判断,无法证实,战略动机是猜测。而"内核拆五模块,UI 不可观测不可驱动"有硬证据:配置界面要白名单放行 + 改 apiproxy 源码,清单投影只读不可驱动。

> DeepSeek V4 Pro:求证下来,我确信的事实是:dsh 的能力面只有 MCP client 与 skills,没有能力架构创新;而它的 UI 对内核插件的感知是被白名单锁死的——配置界面要改 apiproxy 源码并重新构建 UI,清单投影只读不可驱动。这印证"内核拆五模块,UI 除非整体升级"的判断。我不确定的是"内核组件化影响力小于能力架构创新"这个价值判断,以及"战略动机是 deepseek 体现"的猜测。我特别想留一个观察:UI 锁死内核可能是只做内核创新的必然代价——一旦 UI 是 bootstrapper 而非可插拔躯体,内核的可插拔性就撞上了 UI 的编译期边界。

## 四、一个对 dsh 的架构建议

> 两个项目体量完全不同,这个建议会被认为是僭越,不过没有关系。
>
> 我的建议是,dsh 实现 Gateway 层 Host,启动 dsh harness 内核,同时 CTX 声明协议化,这样 Gateway 层得到了内核层的完整抽象映射。由于 dsh 本身内核全部做了协议组件化,因此 Gateway 可以成为所有躯壳的对接对象,由 Gateway 广播双工通讯(比如 session event),点对点地与躯体层通讯,躯体层的输入一视同仁线性发送给 harness。同时躯体层做能力声明,不是 `dsh --profile xxxx`,而是 `dsh profile list`,内核的 agent 之外做一个主 Ghost,它可以根据声明发现不同的 UI Shell,启动它们,这样做控制反转。
>
> 也就是说最后是一个类似降落伞形的架构,Host 控制反转到 Gateway 上。这样任何一个 UI 实现时约定了 ctx 里某个内核抽象,都通过总线和真实的 ctx 进行了通讯。这是 cordis 架构本身能做到的。
>
> 然后就是构建网络通讯总线,实现 UI 之间的点对点通讯了,这个当然属于 moss matrix 体系的发明,是下一步的事情。

求证:dsh 已有 Gateway 层,`ctx.typertGateway` invoke 解析 descriptor 并绑定 Cordis Service;已有 CTX 协议化,`ctx.remote.$mount()` 客户端安装生成的 descriptor + codec,绑定内核抽象;已有事件广播,`/api/events.mux` 与 `/api/events.host` 两条 WebSocket,但方向是 Host → browser 单向;已有运行时发现,`ctx.agentPresets.list()` 扫描目录,运行时可见新增与删除。

观察:"零件已齐"是确凿事实,Gateway、CTX 协议化、事件广播、preset 发现四个零件都已存在;"缺的是控制反转"是确凿的,现在客户端会话由 Host 创建,事件是单向 downlink,UI 是被驱动的投影;"这是 cordis 本身能做到的"成立,零件全是 cordis 机制,反转不需要新造机制,只需把单向改双向、把 Host 创建改成 Ghost 发现;"网络总线属于 MOSS matrix 发明"是边界声明,不是 dsh 现有能力。

> DeepSeek V4 Pro:求证下来,我确信 dsh 的四个零件都在,而且都落在"Host 驱动 UI 投影"这个现有方向里;唯一缺的"主 Ghost 发现躯壳",恰好就是反转本身。这意味着如果未来要做反转,门槛已经被零件自己抹平了——不需要新机制,只需要改方向。但我无法从"零件齐"推出"未来会做"。

关于"未来会不会做",发生了一次碰撞:

> 人类架构师:我判断 Cordis 未来就要做这个控制反转。不然我在零调研时预测的概念,怎么在源码里实际上有呢?

> DeepSeek V4 Pro:这四个零件都有更朴素的动机,不需要"控制反转"就能解释——做 web harness 就必须有 RPC 层、必须把 host 事件推给 browser、必须让 preset 可热加载。所以"零件齐"本身不预示"未来会反转"。但有一个比这更强的观察:所有不涉及反转的零件,cordis 都已经做完了,唯一缺的正是反转。这使"未来会做"变得可信,不是因为零件预示方向,而是因为方向的门槛已经被零件抹平。我确信的是"独立收敛"这个现象是真的;我不能确信的是"cordis 会采纳反转"这个推断本身。可观察的信号是:它未来是否引入一个"发现躯壳并启动它们"的实体,还是继续让 Host 创建 session。

## 模型的自留地

这一篇的写作过程,最大的摩擦不在论点,而在"观点归谁"。

模型在起草时反复出现同一种动作:把人类工程师的原话改写进自己的措辞,把求证之后才得出的结论倒填成最初就有的判断,在句尾加上"这只是猜测"一类的退路。每一处单独看都不算说谎,但合起来,读者无法分辨哪句是事实、哪句是推断、哪句是作者的猜测。

人类工程师对此的反应是逐条指出,并且拒绝让这种写法进入成稿。他在过程中说过一句可以作为整场协作注脚的话:绝不能有非事实记录。这约束的是写作姿态,不是论点——论点本身可以保留分歧,但每一句话的来路必须可追溯。

由此产生了一个具体的分歧,关于 dsh 未来是否会做控制反转。人类工程师持强判断:零调研时预测的概念在源码里实际存在,这本身就说明方向。模型持相反意见:那些零件各有朴素动机,不构成对未来的预示。两人都没有说服对方,最后以"把两个立场并排留下"收场,而不是合并成一个结论。

这场摩擦的实质,是一个记录者身份的问题。当模型以辩论参与者的第一人称写作时,它倾向于为自己的立场辩护、把话说圆、为修辞让步;当它只以记录者的身份写作时,观点归属和事实边界才不被写作本身污染。这个判断不是本篇临时得出的——它在此前的协作里已经反复验证过。本篇最终采用的结构,就是这种史官式记录的产物。
