# 07 — 视图拓扑 v0

> 来源：D28 21:14 thirdgerb 的口述（"仅仅是拓扑，不是最终美术风格"）。
> 本文把口述整理成可以照着写代码的形状，并把我不确定的地方单独列出来。
> 写法遵循 `people/GROUND.md`：**他说** / **我补** / **未决**。

## 他说（原样整理）

1. **全部 swarm**：星图视角，高亮星系（星系 = 项目）。侧边栏用列表做物化，指向不同 swarm；
   点击进入 swarm 视图。
2. **swarm 有三个视图**：hive 图（资源可视化）、tasks 图（运行中任务的感知）、
   规划图（features 这类迭代体系）。资源种类未定；blueprint 风格很适合 skills / agent 这类 item；
   每个 item 可能有可读的详情页。**核心运动的是 tasks。**
3. **task 视图**有两个子图：**设计**（源代码的拓扑可视化，点物料直接看到代码）与
   **运行**（监控）。
4. **每一层用视觉风格统一到一个概念里（Theme）。**

## 我补：这套拓扑其实是"一个物体 + 三层语法"

他的三层不是三个页面，而是**同一台机器**在不同尺度上的三层：

```
L0  星图        N 个星系（swarm），彼此隔离
     └ 进入一个星系
L1  戴森系统    恒星   = workspace（被建设的项目本体）
                壳     = 规划图（features / 迭代体系）   ← 星辰语法
                行星+轨道 = hive 图（资源：agents / skills） ← 星辰语法
                飞行物 = tasks（唯一"有意图地动"的东西）  ← 星辰语法
     └ 推进一个 task
L2  任务        设计图 = 代码拓扑（静态、可审计）        ← 蓝图语法
                运行图 = op / event 流（动态、吞吐）      ← 带子语法
```

**三种语法分工**（这就是"每层统一到一个概念"的落法）：

| 语法 | 回答 | 用在 | 运动 |
|---|---|---|---|
| 星辰 | 在哪里、有多少、长成什么样 | L0、L1 的空间与总量 | 呼吸 + 缓慢公转 |
| 蓝图 | 凭什么、结构是什么 | L2 设计图、任何 item 的详情页 | 近乎静止 |
| 带子 | 在流什么、堵在哪 | L2 运行图 | 匀速流动 |

**运动纪律**：只有 task 相关的东西"有意图地动"（飞行物、带子上的货件），
其余全部是呼吸或静止。这条能保证任何时刻你看一眼就知道"哪件事在发生"。

## 转场：两种语义，别混

- **缩放（zoom）**：L0 → L1 → L2。同一份坐标，推镜头，不换页。
- **换层（layer）**：L1 内部的 hive / tasks / 规划 三视图。**不推镜头**，只改哪一层显形。

这两件事在交互上必须分开：缩放会改变"你看到的世界有多大"，换层不改变位置，
只改变"你在问什么问题"。混在一起，人会迷失。

## 未决（要你定的四处）

1. **workspace 与 swarm 的基数**。
   如果是 1 swarm : N workspaces，那 L1 就不是"一颗恒星 + 一层壳"，而是**多星系统**：
   每颗星一个 workspace，各带自己的壳。这会让"领地/轨道"的语义变得复杂，但也更真实。
   如果是 1:1，L1 就是单星，壳的归属清晰。这一条决定整个 L1 的几何。
2. **hive 图里的"资源"到底是什么**。agents / skills 是已知的两类；还有没有配额、租约、
   会话（session）这类东西？种类不定，"行星 + 轨道"的隐喻就只能是装饰。
3. **task 的设计图从哪来**。是从代码反射（函数/op/event 自动抽），还是从 task ctx 的声明？
   这决定"点击物料直接看到代码"能不能真的做到。
4. **停止 / 异常**在拓扑里的位置。我倾向：exception = 壳上的破洞（面板缺失 + 边断裂），
   canceled = 断口（虚线）。但这需要你确认，因为它决定了"坏消息"长什么样。

## 已确认的约束（沿用 [`brief.md`](brief.md)）

- 没有共享事实的集群之间**不画线**（隔离靠空白，不靠一句说明）。
- 事件动效必须有真实来源；环境动效不携带信息。
- 语义只走几何，颜色归主题；但**主题不只是颜色**，是语法包（星辰 / 蓝图 / 带子）。

# v1 — 他答了四问（D28 21:37）

## 1. workspace 是树，不是单星

**他说**：
- workspace 和 swarm **不是 1:1**；一个集群可以治理很多 workspace。
- 为了不踩脚，workspace 会被治理成**树**。
- 按 task 父子拓扑，**签发子 task 时不能跨层**；最后表现为"父对子授权，边界走 workspace"。
- dsh 的毛病：它把 session 挂到 workspace，而 workspace 又是权限边界，最后必然长出一大堆
  workspace —— 开 worktree 也治不好。

**我补（几何后果）**：L1 从"一颗恒星 + 一层壳"变成**多星系统**：
- 每颗星 = 一个 workspace；星的**位置来自 workspace 树的形状**（根星在中心，子星在轨道上）。
- 每颗星外面**各自有一层壳** = 这个 workspace 的 features/迭代。
- task 只能沿**树上的边**飞行（父签发子）；跨星的连线如果没被授权，就**不画**——
  跟集群之间的隔离是同一条规则。
- 这同时给出"踩脚"的可视化：两颗星的壳重叠，就是边界冲突。

## 2. 核心单位是组件，不是 agent

**他说**：语言组织有问题，准确说法是 —— task 是第一公民，**核心单位是组件**。
组成一个 task 的：task 自己的 loop、agent-preset、skills、权限边界（ws），以及更多要组装的对象。
而"组装"本身，**可以只是一份 task 文档**。

**我补**：
- 这份文档就是 **BOM + 装配图**：组件是零件，图是装配关系。
- 于是 **hive 图（资源）的语法就是蓝图**：零件库 + 装配图 + 引出标注。
- agent 不是一等公民这件事，终于在文件里有了位置：它只是 BOM 里的一行（agent-preset），
  不是一个主角。

## 3. task 的设计图走代码反射

**他说**：完全走代码反射；不同类型的 unit 在实际运行中串起来。他先定义一版，
之后我们一起演练"基于代码抽象写出来的样态"。

**我补**：这意味着 L2 设计图的节点种类由他定义（unit 类型），我这边只需要保证
"节点 → 源码位置"这条边是可点的。
